## 1. 结论与定位

**Muxterm 是日常使用的跨平台原生终端，原生集成 tmux / Herdr，并可按 Project 组织本地和远程工作。**

首先满足普通终端的使用方式：打开即可使用 shell，不要求先创建 Project、安装复用器或运行 agent。
Project、复用器集成和阅读视图按需使用；默认界面保持简洁。这里定义目标体验，具体首次启动流程仍需验收。

项目负责人的持续使用理由已经明确：现有 Project 保存方式符合自己的习惯，
tmux / Herdr 都在实际工作流里，希望继续用这一扇窗口处理它们，直到编码习惯发生明显变化。
Agent 是终端中的重要程序；服务、测试、日志和人工命令也属于同一个工作现场。

目标还包括让其他用户长期日用，因此需要可理解的默认行为、可靠发布和持续兼容，不能只对开发者自己的环境好用。
当前应当完成日用交互并趋于稳定。下一阶段是编辑框、输出阅读/批量复制、图片投递与呈现、远程文件打开；
已有端口转发继续完善完整链接打开与状态反馈。**ACP 客户端优先用现成工具，本轮不接入 Muxterm。**

个人使用验证需求，外部用户使用验证产品能否离开作者的环境。两者都比是否占据独家市场更有用。
跨 Runtime 和 Project 工作方式是当前的使用理由，不足以推导出商业护城河。
不宣称 Muxterm 是唯一同时兼容 tmux / Herdr 的终端：本次有限检索不能证明唯一性。

## 2. 新情况怎样改变旧判断

| 已核实的情况 | 对 Muxterm 的含义 |
| --- | --- |
| ACP 规范提供 prompt、流式响应、工具调用、权限请求；支持相应能力的 agent 可加载或恢复对话 [1–3] | 以对话、审批、阅读改动为中心的用户，采用成熟结构化客户端通常更直接。不能把 ACP 描述成只会发消息、无法恢复上下文 |
| ACP 也定义了可选的终端命令能力；远程 transport 的标准化仍在推进 [4–5] | 不能说 ACP 与终端毫无重叠；但协议本身不等于任意既有 tmux / Herdr 工作区的完整客户端 |
| Rex 于 2026-10-05 宣布开始公开测试，首批为 macOS；官方承诺客户端和服务端免费、无需账号、可自托管 [6] | 撤销“对手只造 Runtime”“原生窗口座位空着”“零账号独有”的旧判断。测试公告不等于全平台稳定发布 |
| Herdr 已有 Ovis、Herdglass、Herdr GUI 等客户端：覆盖浏览器/手机、原生 macOS、多主机、状态与终端等不同组合 [7–10] | 只服务 Herdr 时，专用客户端是合理替代品；Muxterm 的存在不能依赖“Herdr 没有 GUI” |
| Pi Web 项目已有结构化会话、文件/差异查看；另一个同名项目也覆盖真实 workspace、后台会话和多机器 [11–12] | “聊天网页”也可能逐渐覆盖工作环境。不能假设持久性、多机器、文件操作永远属于终端产品 |

这里核对的是协议和项目自己的公开说明，没有进行竞品安装或质量评测。
用户所说的 `herdrui`、`pi-web` 未唯一定位到仓库；表中列出确切项目作为同类例证，
不把同名项目混为一谈，也不据此声称 Pi Web 使用 ACP。

旧报告中“不会做 GUI”“聚合没人做”“投递通道拿不走”“赶在 Rex beta 前发布”等推断不再作为依据。
也不因竞品出现就改写成“必须转型 AI 工作台”：当前真实用途仍然成立。

## 3. ACP 与 Muxterm 如何取舍

| 实际工作方式 | 优先选择 |
| --- | --- |
| 主要发 prompt、看结构化回复与 diff、批准工具调用 | 成熟 ACP 客户端或 agent 自己的 GUI |
| 工作全部在 Herdr，专用 GUI 的操作和项目组织已经合适 | Herdr 专用客户端即可 |
| 本地/远程混用 tmux、Herdr、shell，项目下并存 agent、服务、测试与日志 | Muxterm 继续作为日用终端 |

ACP 的价值是结构化 agent 交互，不要求 Muxterm 承接这一产品。
现阶段另用成熟客户端，避免维护第二套会话、模型设置和权限交互。
后续按需提供只读的 agent transcript 阅读，不等于接管其生命周期或实现完整聊天客户端，见 §5.6。
需要跳到外部工具时可以提供明确入口；不承诺两个客户端共享同一条正在运行的对话。
ACP 的 load/resume 能力不自动意味着可以接管任意终端 TUI 中的现有进程。

仅在以后持续出现“同一项目必须在两个工具反复切换，而且明确的协议集成能消除这个成本”时，
才重新评估接入。届时另写产品提案；不先造 `AcpRuntime`，不让 ACP conversation
冒充当前 Runtime 所提供的 Tab/Pane，也不为未来可能性提前重构 Core。

若以后所有工作都搬到 ACP GUI 或单一 Herdr 客户端，Muxterm 可转为低频维护甚至停止扩展。
这不是当前要追求的结果，也不需要为避免它不断加功能。

## 4. 已有基础与维护主线

Project / Worktree 组织、Runtime × Transport、WorkspacePool、Tab/Pane、原生终端界面
继续保留。使用者已经认可的打开和保存习惯，应当作为兼容承诺来维护。
不为重新讲产品故事改变产品树，不把 Project、git worktree、Runtime 的会话混成同一概念。

稳定性是后续每一项功能的前提，优先处理实际复现的问题：

- 输入、中文 IME、多行粘贴、选择复制、滚动、缩放与 resize 的正确性。
- 多工作区切换和大量输出时的响应；一个 pane 不应拖住其它工作。
- SSH 中断、休眠唤醒、重连、客户端重启后回到正确目标；恢复以 Runtime 实际能力为准。
- 明确区分客户端断开、进程退出和关闭工作区，不误终止用户工作，不把普通 shell 承诺为持久会话。
- 设置、安装、更新的可靠性，以及 macOS / Linux 已有核心行为的一致性。

这些是维护责任，不是重新制造通用终端内核、SSH 系统或多路复用服务端的理由。
文档里有某个模块或类型不等于体验已经通过验收；本轮不声称上述项目全部完成。

## 5. 接下来做什么

### 5.1 独立编辑框：下一个完整功能

让用户在 Muxterm 自己的编辑框中准备内容，再明确发送到选中的终端/agent。
支持多行、中文输入、复制粘贴和按目标保存草稿；目标机器、Project、工作区/pane 要始终可辨认。
切换工作区不会把未发送草稿悄悄改投到另一个目标。终端中的直接键盘输入继续保留。

第一版专注“编辑 → 检查目标 → 投递”。发送记录只表示投递结果，不能伪装成完整 agent 对话。
不加入自动改写 prompt、模型调用、群发 agent、自动排队执行或推测式审批。

**必须区分终端写入与 agent 收到消息。** 当前路径面对的是终端程序，可能在 prompt、
选择菜单、运行工具，也可能已经退出回 shell。向通道写入成功不等于 agent 已接受。
目标断开、退出或身份变化时保留草稿并阻止旧目标自动发送；状态不明确时让用户查看终端，
不得凭一段文字猜测就自动提交、重试或按回车。不同程序的粘贴/提交行为需用实际样例验证。

完成标准：在日用 tmux 与 Herdr、local 与 SSH 场景中，长文本和中文可编辑，
切换目标不串草稿，失败不丢内容，重连不重复发送，原有终端操作不受影响。

### 5.2 图片投递：复用现有工作流

沿用负责人已在使用的“复制图片 → 经 SSH 放到远端 → 使用远端路径”的方式，接入编辑框。
图片在草稿中有缩略图、文件名及上传状态；人可以移除附件，最终投递内容中使用正确目标的路径。
上传到机器 A 的路径不能随目标切换直接发给机器 B。上传失败保留草稿，不发送无效路径。

图片发送是明确的工作区附件投递，不扩张为全局剪贴板同步。
先复用现有投递约定，不同时增加云存储、附件服务或一套 agent 专属上传协议。
后续维护需明确临时附件保留期限，避免重开草稿引用已经清理的文件。

完成标准：截一张图，在编辑框配上说明，发给远程 agent；图片位置可见、失败可重试、目标不混淆。

### 5.3 图片呈现与远程文件打开：完成读取结果的闭环

用户还需要看 agent 生成的图，以及点击终端里出现的远程文件。
这属于“输入材料 → 工作执行 → 查看结果”的同一流程，有理由进入后续路线。

图片呈现区分三件事：编辑框的附件缩略图、点击文件后的预览、终端输出中的内联图片。
**负责人本轮确认：点击预览和终端内联图片都需要。** 两者分别交付和验收，
不自动构成对所有格式或所有终端图像协议的承诺。实施前用日用程序实际输出的图片样例
确定首批格式和协议，打通从正确机器取得并显示图片的完整路径。
终端内联图片涉及 Surface 与 Runtime 链路，需分别验证 tmux / Herdr 与 local / SSH，
不支持的组合明确说明并保留文件预览入口；不能只加一个本地图片控件就算完成。

远程文件点击必须保留“机器 + 路径”的含义：

- 本地路径交给系统应用或用户选择的编辑器；目录可在系统文件管理器中打开。
- 远程图片/文件由对应连接取得，按类型做有限预览，或下载副本交给外部应用。
- 需要编辑远程源文件时，优先交给已支持远程工作的外部编辑器；下载副本不暗示自动回写。
- 相对路径需要可靠 cwd；路径不明确时提供复制或定位信息，不误打开本机同名文件。

保留这类点状入口，不在 Muxterm 中建设完整文件树、通用文件管理器、代码编辑器和双向同步。
图像协议、富文档预览和嵌入浏览器都按真实样例单独取舍，不一次性覆盖。

2026-10-29 补充：Ghostty 1.4 的 HTML 相关能力主要是剪贴板 MIME 与终端内容格式化，
不作为内嵌网页渲染的依据。当前锁定的 SwiftTerm 已声明支持多种图像协议；
先验证现有 local/SSH × shell/tmux/Herdr 链路与恢复，再决定是否需要换内核。
公开 libghostty-vt 提供终端状态而非完整原生控件，暂不迁移；具体评估条件见
[`TERMINAL-CAPABILITIES.md`](TERMINAL-CAPABILITIES.md)。HTML 报告优先外部浏览器打开。

完成标准：受支持组合中的实际终端图像输出能正确显示；从远程 agent 输出点击实际存在的图片或文件，看到正确内容，知道来源机器；
路径失效、权限不足和连接失败可理解，且不会误导用户编辑了本地副本却以为远端已改变。

### 5.4 导航、搜索与状态：修好已有能力

Project / Worktree 切换、返回上一个现场、已连接工作区内的搜索和命中定位，继续按日用问题打磨。
Activity 帮用户发现需要介入的地方，点击后到正确终端；它不成为完整聊天记录或任务看板。
可信结构化状态优先；推断和未知状态不伪装成精确的等待输入。撤销旧清单对未知程序“零误报”的承诺。

不为搜索新增跨天日志库、知识库或 AI 总结服务；不因竞争对手有更多 agent 卡片而维护一整套专属 UI。

### 5.5 端口转发：把发现、转发与打开连起来

仓库已有输出 URL 端口识别、目标机监听扫描、异步转发、停止/忽略和 LAN 切换；
macOS 也有打开/复制入口。下一步完善用户点击原始链接后的行为：绑定来源目标，建立或复用转发，
保留协议、路径、参数与 fragment 后交给外部浏览器，显示 pending/失败和实际本地端口。
当前端口识别仅保留端口数，打开入口拼接 HTTP 根地址；完整链接打开尚未完成。

转发由用户发起，默认本机回环；扫描到端口不自动转发。区分网页服务与一般 TCP 监听，
完善关闭/重连后的状态与 IPv6。手输任意端口尚非现有能力，按需求另行补充。
不做公网隧道或完整浏览器工作台；不必等待终端内核评估，也不自动阻塞编辑框和稳定版发布。

### 5.6 输出阅读、批量复制和折叠

这是普通终端的自然增强，可服务命令、编译输出、日志和 agent。先做明确范围的大段复制、
保存文本、稳定阅读；命令边界完整时，再做按命令选择、复制和折叠。
默认保持原终端，阅读视图按需打开，折叠不改写 live Surface。

截图中的 agent 轮次、回复与工具调用分组则需要结构化来源。
ACP 不是唯一方案，原生 transcript 或事件接口也可以；但单纯 ANSI/画面解析不能保证通用准确。
有需要时仅为高频 agent 探索只读阅读，不扩大为全 agent 聊天客户端；无可靠来源就回到普通文本。
可行性、仓库已有基础、缺口和验收见 [`OUTPUT-READING.md`](OUTPUT-READING.md)。

### 5.7 可选扩展：先调用外部工具

允许用配置好的命令/打开动作增强终端，例如在当前目标与 cwd 新开 pane 运行文件管理器，
或把路径交给外部编辑器。默认界面不增加完整文件树，工具缺失与执行位置可辨认。
先落地实际动作，再提炼必要接口；不先建通用插件 SDK、Web 面板或市场。
扩展复用宿主的目标管理和动作入口，不拥有连接池或第二个事件泵。
边界与文件管理器参照见 [`TERMINAL-CAPABILITIES.md`](TERMINAL-CAPABILITIES.md)。

## 6. 当前不做什么

- ACP 客户端、全功能聊天 UI、模型/账号管理和跨客户端对话同步；只读 transcript 阅读是受限探索例外。
- Agent 编排、自动任务派发、自动审批、看板和多 agent 广播输入。
- 完整 IDE、文件管理器、Git GUI、文件同步系统、通用文档阅读器、内嵌浏览器。
- 为跟进竞争对手新增 Runtime、自研多路复用器或直接替换终端内核；libghostty 仅在实际兼容性、性能或跨平台维护需求下做有边界的对照验证。
- 手机客户端、云服务、账号体系、协作平台、插件市场、持久化全局历史索引。

“点击路径后交给外部工具”“预览工作区生成的图片”不等于建设文件管理器；
“为已有终端提供编辑框”也不等于实现 ACP 客户端。按实际承担的职责划边界。

## 7. 开发顺序与何时算完成

| 阶段 | 要交付什么 | 退出条件 |
| --- | --- | --- |
| 持续维护 | 修复会影响日常使用的输入、显示、连接与目标识别问题 | 没有已知会丢输入、投错目标、误结束工作或持续阻断日用的问题 |
| 下一项功能 | 独立编辑框 + 复用图片投递 + 草稿/失败处理 | 能完成真实长文本与远程截图输入；直接终端操作仍然顺畅 |
| 通用输出改进 | 批量复制、阅读输出；可靠边界下的命令分块/折叠 | 大段内容可准确复制，已淘汰/缺失内容不伪装完整，不影响 live 终端 |
| 随后 | 图片呈现 + 远程文件点击打开 | 能从真实输出读到正确机器上的结果；明确支持范围与外部打开方式 |
| 按需增量 | 完整 URL 转发打开、导航/搜索、调用外部工具 | 消除反复出现的实际绕路，不创造另一套工作台 |
| 稳定期 | 缺陷修复、兼容性、性能、发布和少量打磨 | 使用者不再为重复问题返回另一个终端；不要求每个版本增加功能 |

不再把旧报告全部愿景当成 1.0 门槛。稳定版本可以分阶段发布，更多图片协议、完整 URL 打开、
菜单栏常驻等未交付项目不自动成为阻塞项；libghostty 和完整插件平台不是发布前提。

建议用连续两周真实使用记录验收，而非再扩张功能表：
记录必须返回其它工具的原因、投递失败/丢草稿/错误目标、连接恢复问题和高频摩擦。
用现成 ACP 或 Herdr 客户端完成更适合它们的工作是正常分工，不计为 Muxterm 缺陷。
没有重复痛点时就保持稳定；终端产品可以完成一组能力后长期维护，不必通过持续加功能证明仍有意义。

新增功能只问：它是否改善当前终端/工作区中的输入、连接、导航或结果查看；
是否在真实使用中反复需要；能否通过调用现成工具解决；能否在不扩大维护职责的情况下交付。

### 让别人长期使用的工作

“简洁”约束的是默认界面与产品职责，不是要求功能永远很少。
[iTerm2 的命令选择](https://iterm2.com/documentation-command-selection.html)、
[kitty 的输出阅读](https://sw.kovidgoyal.net/kitty/shell-integration/)、
[Ghostty 的 shell integration](https://ghostty.org/docs/features/shell-integration) 都把增强放在终端工作流中；
[Alacritty 官网](https://alacritty.org/) 明确强调通过与其它应用集成提供功能。
Muxterm 采用同样的取舍原则，不以复刻这些产品的完整功能表为目标。

- **上手**：用户安装后能立即开普通 shell；再按需打开已有 tmux / Herdr 和保存 Project。
  提供短文档与真实截图，讲清默认快捷键、关闭/断开的含义，不要求先理解内部架构。
- **发布**：小版本、清晰变更记录、已知问题和支持范围；配置兼容与迁移可预期，更新不扰乱已有工作。
- **兼容**：持续验证 macOS / Linux、常用 shell、SSH、tmux/Herdr 与全屏 TUI；对输入、Unicode、
  resize、休眠恢复等真实回归保留样例。终端质量比新增管理面板更重要。
- **外部验证**：先邀请少量不同环境的日用用户，关注安装失败、必须退回原终端的原因和持续使用情况。
  不用星数或更多按钮替代留存；不把每个人的 agent 工作流都纳入主线。
- **维护预算**：为缺陷、兼容和文档留固定精力；功能数量受维护能力约束。没有强需求时允许只发布修复版本。

公开价值主张是“一个顺手的普通终端，能把已有 tmux / Herdr 工作区自然带进原生界面”。
Project 保存是对重度用户的增强，不成为普通用户的入门负担。
