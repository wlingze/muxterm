## 1. 结论

**大量复制、命令输出分块和折叠不需要 ACP。准确的 agent 轮次/工具调用分组需要结构化来源，ACP 是可选来源之一。**

用户截图包含两种需求：更容易读和复制长输出，以及按对话轮次呈现 agent 的消息和工具活动。
先交付第一种。第二种保留为有明确收益时的可选、只读阅读视图，不能用正则猜画面的方式承诺通用支持。
默认仍然是普通终端，阅读视图由用户主动打开，不把所有输出改造成卡片流。

## 2. 三种能力不要混为一谈

| 能力 | 需要的数据 | 是否需要 ACP | 建议 |
| --- | --- | --- | --- |
| 复制长段、最近 N 行、当前保留的输出；导出文本 | 可信的终端历史/文本快照 | 不需要 | 优先做，适用于 shell、测试、日志与 agent |
| 按 shell 命令跳转、选择、复制和折叠输出 | shell integration 提供命令边界，如 OSC 133 | 不需要 | 在边界完整的情况下提供；无集成时退回普通文本 |
| 按 agent 用户轮次、回复、工具调用折叠/复制 | 原生 transcript、事件接口、RPC/SDK，或 ACP | 不强制 | 后续只对明确支持的来源提供只读视图 |

[iTerm2 Command Selection](https://iterm2.com/documentation-command-selection.html) 已提供按命令限制选择、搜索、复制/保存；
[kitty shell integration](https://sw.kovidgoyal.net/kitty/shell-integration/) 支持选中整条命令输出与交给 pager 阅读；
[Ghostty shell integration](https://ghostty.org/docs/features/shell-integration) 也支持命令输出选择与 prompt 导航。
这些都是普通终端的增强，不以 agent 协议为前提。shell 集成与 muxer/SSH 的组合仍需逐项验证。

## 3. 直接解析 shell 能得到什么

例如在 shell 启动一个 agent，随后在 agent 里对话 30 轮：shell 通常只看到“一条 agent 命令还没结束”。
它不知道第 12 轮在哪里、某段文字是回复还是工具输出。OSC 133 的 shell 命令边界不能替代 agent 消息边界。

终端数据也不是天然的逐条日志：程序可能移动光标、覆盖旧内容、使用备用屏、折叠工具输出或在 resize 时重绘。
把收到的原始字节去掉 ANSI 再拼接，可能得到重复、残缺或错序的文本；已经覆盖或未显示的信息无法凭画面还原。
角色名、分隔线、颜色等只能构成特定程序版本的启发式，不足以支撑可靠的对话浏览器。

因此，普通文本提取可以做；“任何 agent 都能自动识别每一轮并准确复制全文”不能作为通用终端承诺。
截图里的轮次数、工具数、token/费用等信息，也只能在来源明确提供时展示。

## 4. 不用 ACP 的结构化路线

[Ovis 的官方指南](https://github.com/devswha/ovis/blob/main/docs/guide.md) 明确说明：
状态来自 Herdr，终端显示 real attach 输出，Chat 读取 agent 自己的 session files，发送进入原来的 live pane。
它为不同 agent 维护不同 transcript reader；没有可靠来源时退回终端。
这证明“终端里运行 agent + 外部折叠阅读”可行，也展示了跨 agent 兼容的维护成本。

[Pi 官方 README](https://github.com/earendil-works/pi/tree/main/packages/coding-agent) 列出 JSON、RPC 和 SDK 等接口。
这些是结构化来源的例子，**不证明 RPC 能直接接管一个已经在 TUI 中运行的任意实例**。
对于 Muxterm 当前“继续操作原 pane”的需求，可核实的只读 transcript 比另起一个控制客户端更值得先评估。

如进入实验，必须解决：

- 把文件/事件源绑定到正确的机器、进程、pane 和对话；不能仅按 cwd 或“最新文件”猜测。
- 远端资料从对应连接读取，不能误读本机同目录的另一条会话。
- 增量写入、半条记录、分支切换、恢复对话和版本变化；无法确认时显示不可用。
- 展示来源和覆盖范围；复制正文、复制整轮和复制工具输出是不同动作。
- 保持只读，不修改 agent 的 session 文件，不从历史权限请求生成仍有效的审批按钮。

先选择使用者最高频的一个 agent 做有边界的实验；收益不足就停止。
不据此建设全 agent 适配目录，不让普通终端的可靠性依赖这些 reader。

## 5. 推荐的第一版产品

提供按需打开的“阅读输出”：保留原终端，另以稳定文本供选择、搜索、复制和保存。
有完整命令边界时可选择某条命令，显示命令文本/退出状态，折叠其输出并一键复制；
边界缺失时允许选择文本区间，不制造假的命令或 agent 回合。

批量复制的范围要明确：当前选区、某条命令、最近 N 行、当前保留历史。
“全部”只指实际可取得的数据。历史被淘汰或出现 data gap 时提示不完整；超大内容可保存为文件。
保留真实换行，正确处理屏幕软换行和 Unicode；复制不把 ANSI 控制序列带进普通文本。
输出持续增长时不打断选择，冻结的是阅读数据，不是后台进程。

折叠发生在阅读视图中。直接把 live VT 中间几行隐藏会改变应用认为的光标/鼠标坐标、滚动和布局，
不能拿重新编码的 ANSI 文本替代原 Surface。仍遵守 `SURFACE.md` 的单面架构。
后续若做默认终端视口内的折叠，需要另行验证其交互和坐标模型，不作为第一版承诺。

## 6. 仓库现有基础与真实缺口

本轮只读确认了以下基础，未把它们当作整项功能已完成：

- `src/core/protocol/terminal/emulate.rs` 的 `CommandMark` 有稳定行 ID、命令文本和退出码；
  **还不能单凭这三个字段证明完整输出起止范围已就绪**。
- `src/core/workspace/pane_buf.rs` 有有界历史、搜索、最近 N 行、命令刻度及历史坐标查询。
- `src/core/protocol/ffi/functions/snapshot.rs` 已经向 frontend 暴露命令刻度；
  阅读数据仍应走统一 FFI/Core 边界。
- `src/frontend/macos/Terminal/TerminalView.swift` 的复制路径使用终端当前选区，不能据此宣称已支持整轮 agent 复制。

后续原型先验证命令边界和可导出文本是否完整，再决定需要补什么数据。
Herdr 的服务端历史与其它 Runtime 的历史路径不同；不能假定一个本地 scrollback 接口覆盖所有情况。

## 7. 验收样例与排期

先用普通 shell 的长输出、多行命令、中文/emoji、软换行、失败命令验证复制；
再验证运行中输出、resize、历史淘汰、断线恢复，以及 local/SSH × tmux/Herdr 的差异。
最终复制内容要与已知原文对比，不能仅凭画面看起来对就验收。

对于全屏 agent，明确允许“只能复制可取得文本，无法按轮次分组”的降级。
可选 transcript 原型另验：同目录两个 agent、会话恢复/分支切换、文件部分写入、来源消失；
不串会话优先于尽量猜出一个结果。

排期：编辑框之后，将批量复制/阅读输出作为通用终端改进推进；命令折叠在边界验证后加入。
Agent 轮次阅读是独立探索项，不阻塞图片功能、普通终端发布，也不把 ACP 列为前置依赖。
