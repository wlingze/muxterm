## 0. 证据基础

### 0.1 仓库侧（只作为背景材料）

| 判断项 | 结论 |
|---|---|
| macOS 前端 | **AppKit**（非 SwiftUI），~46 个 Swift 文件；本地 shell + 本地 tmux `-CC` 的 tab/嵌套分割/命令面板已被 XCUITest 覆盖 |
| Linux 前端 | GTK4 + VTE4，本地 shell tab/split 有集成测试 |
| 其他前端 | TUI（crossterm/ratatui）+ CLI + 本地 daemon，均可跑 |
| SSH 远程 tmux | 代码路径存在（macOS QuickConnect / TUI wizard），但端到端测试是 `#[ignore]` / 无 sshd 即跳过；`phase1-summary.md` 自述未做真机验证 |
| 多工作区同时在线 | `ConnectionPool` + `WarmConnectionSlot` 只有纯逻辑单测（FakeSlot），自动化测试层面没有 E2E 覆盖。**但 2026-08-13 的一整天真实使用已在产品层验证成立** —— 缺的是回归保护，不是能力 |
| 搜索 | `ScrollbackBuffer::search` 有单测，**未接任何 UI**；Linux 命令面板的 `Action::Search` 是空实现 |
| Agent 感知 | **不存在**。仓库里的 "agent" 只表示"渲染 agent 的高频重绘"这一性能问题 |
| 通知 / 设置界面 / 移动端 | **不存在** |
| daemon | 是 CLI/TUI 用的本地 unix socket IPC helper，**不是 control plane**；macOS GUI 走 FFI，根本不经过它 |

架构文档层面已经写死的产品赌注：Core Protocol（Session→Window→Tab→Pane）是产品本体，
**tmux 是可替换的 Runtime 而非产品本身**（`「Runtime 可扩展：ShellRuntime、TmuxRuntime……未来 ZellijRuntime」`），
SSH 是 Transport 不是 Runtime，v1 明确 `「不在 v1 支持多 session 同时活跃」`。

### 0.2 外部市场（联网核查，2026-08-13 23:05–23:12 CST）

**A. "tmux `-CC` 原生 GUI" 这个位置已经不空了。**

| 项目 | 形态 | 与 Muxterm 的重合度 |
|---|---|---|
| [ivyTerm](https://github.com/janakdr/ivyterm) | `gtk4-rs` + VTE4 + tmux control mode，支持本地与 SSH 远程 tmux | **技术栈与 Muxterm Linux 端几乎完全一致** |
| [Dispatcher](https://github.com/bobrenjc93/dispatcher/) | Tauri + React + xterm.js，tmux `-CC` 本地/SSH，tmux window→tab、pane→split，macOS/Linux/Windows | 产品形态高度重合，且**已经三平台** |
| [kmux](https://github.com/futpib/kmux) | Konsole fork，tmux `-CC` → 原生 tab/split | Linux 侧直接竞品 |
| [tmex](https://github.com/krhougs/tmex) | Ghostty WASM 终端 + tmux control mode + **本地与 SSH 设备并排管理** + BEL/OSC 9/99/777/1337 通知 | **与 Muxterm 的"愿景"重合度最高的一个** |
| WezTerm | 已在推进 tmux control mode 支持 | 体量碾压 |

结论修正（2026-08-13 二轮，采纳项目负责人反馈后）：
**"把 tmux pane 渲染成原生 tab" 确实只是入场券，但这些项目与 Muxterm 不在同一个产品命题上。**

逐个核实下来，它们共享两个结构性选择，而这两个选择恰好是 Muxterm 明确不做的：

| 结构性选择 | 它们 | Muxterm |
|---|---|---|
| **组织单位** | 设备 / 连接（tmex 的 device tree、Dispatcher 的 project-per-tab、ivyTerm 的一次 attach） | **工作区 = 项目 = 一个 tmux session** |
| **导航形态** | 常驻侧边栏（鼠标优先、占用固定视觉面积） | **命令面板（键盘优先、零常驻面积）** |
| **attach 的语义** | 一个**动作**：连上去，然后你就在里面了 | 一个**注册**：连上之后它进入一个可随时秒切的池子 |

**iTerm2 的具体行为已核实**（[官方文档](https://iterm2.com/documentation-tmux-integration.html) + [wiki](https://gitlab.com/gnachman/iterm2/-/wikis/TmuxIntegration)）：
2.9 之后确实可以同时 attach 多个 session，但**每次 `tmux -CC attach` 打开一个独立的 iTerm2 窗口**，
tmux window 成为该窗口内的 tab。于是 N 个 session = N 个窗口 × M 个 tab。
它提供的 tmux Dashboard 是一个管理面板，不是切换器。**"窗口爆炸 + 没有统一切换器"是真实且精确的痛点。**

**但必须诚实：这不是技术护城河，是产品品味。** 侧边栏 vs 命令面板、设备为单位 vs 项目为单位 ——
任何人都可以抄。让它变得难抄的是另外两件事：
1. **Runtime 无关的广度**（tmux + Herdr + 本地 shell，本地 + 远程，全在一个切换器里）——
   这需要 Muxterm 已经建好的四层分层，是真的有壁垒的部分；
2. **原生、极轻、极快**。

**在 20 个工作区的规模上，侧边栏会退化成"另一个需要翻找的列表"，而模糊搜索不会。**
这是 Muxterm 这个选择在**规模上**真正成立的理由 —— 也意味着 Muxterm 应该始终假设"工作区很多"，
而不是"工作区有几个"。

**B. "手机上看/控 coding agent" 是红海，且被 agent 厂商一方免费覆盖。**

- **OpenAI**：[Codex 进入 ChatGPT 手机 App](https://openai.com/index/work-with-codex-from-anywhere/)（2026-05-14 预览）。安全 relay 打通"笔记本 / devbox / 远程环境"，手机上可跨 thread 工作、看终端输出与 diff、审批命令；同时 **Remote SSH GA**，桌面端自动读取 `~/.ssh/config`。
- **Anthropic**：[Claude Code Remote Control](https://code.claude.com/docs/en/remote-control)（2026-02-25 research preview）。`claude remote-control` + 扫码，claude.ai/code 与 Claude 手机 App 直接驱动本机会话；纯出站连接，不开入站端口。此外 [桌面端重做](https://claude.com/blog/claude-code-desktop-redesign)（2026-04-14）已经加了**并行 session 侧边栏 + 内置终端 + 文件编辑器 + Mac/Linux 的 SSH 远程 session**。
- **第三方**：Happy、CC Pocket、Tactic Remote、Agents At Work、AnyCoding、MuxAgent、Cmd+Ctrl —— 至少 7 个，全部是"守护进程 + relay + 手机 App + 推送审批 + E2E 加密"的同一套配方。

结论：**手机端是 Muxterm 最不该碰的方向。** 它要求 relay / 账号 / 端到端加密 / 推送 / 安全模型，而这条赛道上你的对手是把它当免费赠品的模型厂商。

**C. 但厂商方案有一个共同的、结构性的盲区。**

Claude Remote Control 只看得见 Claude 的 session；Codex 手机端只看得见 Codex 的 thread。它们全都是
**per-vendor、per-agent、per-harness** 的。没有任何一个能回答：

> "我 4 台机器上 40 个 pane，哪些在跑、哪些卡住了、哪个在等我？"

其中大部分 pane 根本不是 agent —— 是 build、是日志、是服务、是数据库、是 SSH 隧道。
**这个盲区就是 Muxterm 唯一真实、且在变大的立足点。**

唯一的例外是 Herdr —— 它确实解决了跨 agent 的可见性，但**只对住在 Herdr 里的 pane 有效**。见下节。

### 0.3 Herdr 专项：最像竞品的东西，其实是最好的 Runtime

[Herdr](https://herdr.dev/)（[`herdrdev/herdr`](https://github.com/herdrdev/herdr)）是一个已经相当成熟的
Rust 终端多路复用器，定位是 *"the runtime your coding agents live on"*。它已经实现的东西，
**几乎完整覆盖了本评审原本给 Muxterm 规划的阶段 C 和阶段 D**：

- **常驻后台 server**，pane 活在里面；合盖、断网、重启机器后 agent 继续跑、布局恢复
- **侧边栏标注每个 pane 的 `working` / `blocked` / `done` / `idle` / `unknown`**，
  跨所有 workspace 汇总 —— 这正是本评审 §6 阶段 C 想做的事
- **开箱检测 20 个 agent**（Claude Code、Codex、Cursor、opencode、Grok、Copilot、Hermes…），
  检测规则是**远端可更新的 manifest**（`server.agent_manifests`），不是硬编码
- **`herdr --remote workbox`** 走 SSH，且**已经实现了"本地剪贴板图片 → 远程临时文件 → 把路径贴进 pane"**
  —— 与本评审 §4.2 推荐的最小可靠版本是同一个设计
- workspace / tab / pane / agent 四级模型，Git worktree 一等公民，通知，插件系统

**关键发现：Herdr 的 socket API 是一个比 `tmux -CC` 设计更好的 Runtime 接口，而且是主动为第三方客户端留的。**

| Muxterm Core Protocol 需要的 | Herdr 提供的 |
|---|---|
| 启动时的全量状态 | `session.snapshot` —— 文档原话：*"a one-time bootstrap snapshot for clients that keep their own local runtime cache"* |
| 增量事件流 | `events.subscribe` —— `workspace.*` / `tab.*` / `pane.*` / `layout.updated` / **`pane.agent_status_changed`** |
| pane 字节流 + 输入 | `herdr terminal session observe\|control` —— NDJSON `terminal.frame`（base64 ANSI）+ `terminal.input` / `resize` / `scroll`。文档原话：***"For third-party bridges that only need rendered terminal bytes"*** |
| 布局树 | `layout.export` —— BSP 树（`pane` / `split`，含 `direction` / `ratio`） |
| 协议稳定性 | 有 protocol version，`ping` / `herdr status` 可查 |

对比之下，`tmux -CC` 给的是一个 1980 年代语义的行协议，还要自己从 `%output` 里反转义。
**Herdr 的接口在语义层面更接近 Muxterm 自己的 Core Protocol。**

**战略含义（双向的，两面都要看清）：**

✅ **接 HerdrRuntime 的收益是真实且巨大的**
- 阶段 C（agent 感知）和阶段 D（图片投递）**几乎可以直接白拿**，省下数月并且永远不用追新 agent
- 它**验证了 Muxterm 架构里最贵的那个赌注** —— 「Runtime 可扩展」如果永远只有一个 tmux，这层抽象就是白付的成本
- Herdr 是 **TUI，没有原生 GUI**（"runs in whatever terminal you already use"，鼠标 + 前缀键）。
  Muxterm 是原生 GUI。**在产品形态上是互补而不是竞争。**

⚠️ **但风险同样真实，必须写下来**
1. **租来的差异化。** 如果 Muxterm 的 agent 感知身份建立在 Herdr 上，这个身份是租的不是自己的。
   Herdr 自己加一个 GUI 客户端是完全自然的下一步（它已经有 sidebar、有 mobile Agents list、有 `--remote`）。
2. **迁移成本不在你这边。** Herdr 要求 agent 跑在 Herdr 的 pane 里。而且 Herdr 文档明说：
   *"Agent detection does not inspect tmux sessions launched inside a Herdr pane."*
   **tmux 和 Herdr 在每个 pane 上是互斥的。** 你现有的 `twork` 工作流全在 tmux 上。
3. **双 Runtime 税。** 每个 Muxterm 能力都要在两个语义差异很大的 Runtime 上都成立。
   这与"收敛"的建议直接冲突 —— 所以**时机比决定更重要**（见修订后的 §6）。

**结论：接，但不是现在，而且不能作为身份。**
tmux 侧仍然必须有自己的、廉价的 pane 状态感知（BEL/OSC + 输出速率），
因为你**绝大部分真实工作会长期留在 tmux 上**，Herdr 只覆盖你主动搬进去的那部分。

## 1. 一句话结论（三轮定案版，2026-08-14）

> **Muxterm 是"拥有自己机器的人"的终端 GUI 客户端：
> 工作跑在一台永不休眠的机器上，由 tmux（未来还有更多 Runtime）托管持久性，
> Muxterm 是望向它的那扇窗 —— 一扇窗、一个面板、一枚红点，
> 一个窗口装下全部在飞的工作区，并告诉你哪一个在等你。
> 它永远是客户端不是运行时，只做随模型增值的功能，永远不需要账号与控制面。
> A（日用）+ B（可见性）+ C（搜索）= 1.0，这个产品以完成为荣。
> 下一步只有一件事：阶段 B —— 其地基（客户端 scrollback）先行。**

**演进备忘：** 一轮结论（收敛主线、不做手机端）与二轮结论（macOS 已验证、缺可见性与搜索）
仍然全部成立，三轮把它们放进了更完整的坐标系（对手是谁、位置在哪、终局长什么样）。
定案的完整版本见 §2.14；对外定位句见 §3.1 三轮修正。

**二轮结论（保留）：**

> Muxterm 的核心产品已经成立 —— 2026-08-13 macOS 端完成并完整 dogfood 了一整天，
> 资源占用低、性能表现好。它现在缺的不是验证，是"多工作区"这条主线的最后两步：
> 让工作区可见（谁在等我），以及让工作区可搜（我记得那个东西在哪）。
> 因此：收敛到这一条主线上，不要扩张到手机端。

**重要修正（二轮）：组织单位不是"机器"，是"工作区"。**

一轮评审把定位写成"多机器终端工作区"，这是错的。`~/.local/bin/twork` 说明了真实的组织方式：

```bash
SESSION_NAME=$(basename "$PWD")      # 工作区身份 = 目录 = 项目
tmux has-session -t "$SESSION_NAME"  # 有就 attach
# 没有就按固定形状创建：Monitor(htop+split) / Workstation / Playground
exec tmux -CC attach -t "$SESSION_NAME"
```

**一个项目 = 一个目录 = 一个 tmux session = 一个工作区。机器在本地还是远程，只是这个工作区的一个属性。**

这个修正不是措辞问题，它改变三件事：
1. 切换器应该按**项目**索引，不是按主机分组；
2. "3 台远程主机同时在线"不是目标，**"20 个工作区随时可切"**才是；
3. 它让 Herdr 的接入变得自然 —— Herdr 的 workspace 也是 `--cwd ~/project --label api`，**同一个单位**。

**现在的主要风险不是差异化没验证，而是范围膨胀**：手机端、跨主机索引、双 Runtime 同时上。

**三轮补充：** 范围膨胀之外，另有两个更根本的风险已在后文确认 ——
**作者失去兴趣**（§2.11.7：护城河是热情，公开发布是对冲，见 §2.14.4）与
**时间窗**（§2.10.5：上下夹缝都在收窄，Superlogical beta 之前是插旗窗口）。

## 2. 产品本质

### 2.1 Muxterm 是什么

**一个常驻的多工作区终端 —— 把几十个并行进行中的项目装进一个窗口。**

它的价值不在"渲染 tmux"，而在**取消"窗口"这个单位**：
你所有正在进行的工作 —— 无论跑在哪台机器、由 tmux 还是别的 runtime 托管 ——
都在同一个窗口里，永远连着，永远一次按键可达。

对照 iTerm2 就很清楚：iTerm2 的 tmux 集成把「一个 tmux session」映射成「一个 GUI 窗口」，
所以工作区越多，窗口越多，你的注意力被窗口管理消耗掉。
**Muxterm 的命题是：工作区数量增长时，UI 复杂度不增长。**

### 2.2 Muxterm 不是什么

- **不是更好看的 tmux GUI**。这层已经有 4 个开源项目在做，且不是护城河。
- **不是 Agent orchestrator**。不派发任务、不管理 agent 生命周期、不做审批工作流。
- **不是 Agent 的移动遥控器**。这个位置已经被模型厂商占了。
- **不是文件管理器 / 网盘 / 同步工具**。
- **不是自己的终端模拟器内核**（SwiftTerm / VTE 就够了）。
- **不是通用多路复用器**。tmux 是基础设施，不是要被重写的东西。

### 2.3 核心用户

**一个人，几十个同时进行的项目，每个项目里还有多个并行任务。**

具体画像：每个项目一个 tmux session（session 名 = 目录名），session 里混着 coding agent、
build、日志、服务；机器可能在本地也可能在远程，但**机器不是他思考的单位，项目才是**。
经常同时有两个以上 AI 跑在不同的 session 里。

他今天的痛点有三层，**从下到上**：
1. **窗口爆炸** —— iTerm2 一个 session 一个窗口，窗口里还有一堆 tab，看不过来。（Muxterm 已解决）
2. **不知道谁在等我** —— 必须一个个切过去看才知道哪个跑完了、哪个卡住了。（阶段 C）
3. **不记得东西在哪** —— "刚才那个报错是在哪个 pane"。（阶段 B'）

**不是**：只有一两个项目的普通开发者（iTerm2 就够）；不用多路复用器的人（没有场景）；
团队协作场景（另一个产品）。

这个用户群确实小众。**但它正是"并行 agent 工作流"正在快速制造出来的那一群人** ——
一年前"同时跑 5 个 agent"是不存在的场景。小众不等于不增长。

### 2.4 核心价值（按顺序，不可调换）

1. **连续性** —— 连接永远是热的，工作永远在那儿，不需要重新建立上下文。
2. **可见性** —— 不用切过去就知道那边什么状态。
3. **速度** —— 从"想到某个工作"到"手放在那个工作上"≤ 1 秒。

注意：单独的"速度"撑不起产品（`fzf` + `tmux switch-client` 已经很快了）。
**是"连续性 + 可见性"让速度变得有意义** —— 快速切换只有在你**知道该切到哪**的时候才值钱。
这是 Muxterm 与所有 tmux GUI 竞品的分界线。

### 2.5 核心循环

```
打开 Muxterm（所有机器已经连着）
  → 一眼看到哪些工作区需要我（可见性）
  → 一键切到那个现场（速度）
  → 处理 / 接管
  → 留在原地继续跑，关掉窗口也不丢（连续性）
```

**当前状态（2026-08-13 实测一整天后修正）：**

| 步骤 | 状态 |
|---|---|
| 所有工作区已经连着 | ✅ 本地成立；远程需继续实测 |
| **一眼看到哪些需要我** | ❌ **完全没有 —— 这是唯一的硬缺口** |
| 一键切到那个现场 | ✅ **已成立，且被评价为"非常好用"** |
| 处理 / 接管 | ✅ |
| 留在原地继续跑 | ✅ tmux 天然保证 |

**循环只差第 2 步。** 这就是"还差一步"的准确含义 —— 比一轮评审判断的乐观得多。
而且第 2 步恰好是**成本最低、差异化最高**的那一步。

### 2.6 为什么"GUI 版的 tmux/Herdr"不是换层皮（一二轮都低估了的一条）

前两轮把前缀键当成"人机工程抱怨"处理，这是错的。前缀键不是 tmux 设计失误，
**它是"身为 TUI"这件事的强制后果**——注意 Herdr 从零重写，仍然选了 `Ctrl+B`。
一个跑在字符网格里的多路复用器，必须把自己**全部的 UI 挤进它托管的应用正在使用的同一块网格**，
于是它**只能**抢按键、**只能**抢屏幕行。

由此得到这个产品最本质的一条论证：

> **GUI 不是 TUI 的皮肤，GUI 拥有一整个 TUI 结构上无法拥有的维度。**

| 能力 | TUI 多路复用器 | GUI 客户端 |
|---|---|---|
| 自身 UI 的位置 | **必须**占用字符网格的行 | 窗口 chrome，不占网格 |
| 快捷键命名空间 | **必须**从应用手里抢（前缀键） | 独立命名空间（macOS 的 `Cmd`） |
| 面板可以多大 | 受网格限制，越大越吃工作区 | 想多大多大，因为它是瞬时浮层 |
| Dock badge | ❌ 不可能 | ✅ |
| 系统通知 | 只能借宿主终端转发（best-effort） | ✅ 原生 |
| 声音 | 受限 | ✅ |

**这直接把 §B.4 的"注意力"论证补全了：**

Herdr 已经证明了 agent 注意力是真实且旺盛的需求 —— 但它只能把结论渲染进侧边栏，
因为**侧边栏是 TUI 唯一能表达常驻状态的地方**。
Muxterm 的机会不是抄 Herdr 的注意力功能，而是：

> **用 TUI 结构上到不了的通道，把注意力送到人那里。**
> Dock badge、系统通知、声音、以及一个不必偷网格行的面板。

这也修正了 §0.3 对"租来的差异化"的担忧：
**检测**可以来自 Herdr（或自己的 OSC/BEL），但**投递通道是 Muxterm 独有的、拿不走的。**
这是互补性最实在的一层。

#### ⚠️ 但"无前缀键"不是免费的：你需要一个不冲突的命名空间

去掉前缀键之后，你的快捷键仍然必须落在某个命名空间里，而这个命名空间必须**终端应用不使用**。

- **macOS：`Cmd` 是天然免费的** —— 终端应用从来看不到 `Cmd`。这是 iTerm2 能做到无前缀的根本原因，
  也是 Muxterm macOS 端在这一点上**结构性优于自己的 Linux 端**的原因。
- **Linux：当前默认用 `Alt`，而 `Alt` 并不干净。** 它与 readline 正面冲突：

  | Muxterm 绑定 | readline 原有含义 | 冲突 |
  |---|---|---|
  | `Alt+D` 水平分割 | `kill-word`（向后删词） | 🔴 高频 |
  | `Alt+T` 新 tab | `transpose-words` | 🟠 |
  | `Alt+R` pane 切换器 | `revert-line` | 🟠 |
  | （另外 `Alt+B` / `Alt+F` / `Alt+.` 是词移动与 yank-last-arg，也在同一空间） | | |

  也就是说 **Linux 端只是把 `Ctrl+B` 前缀换成了一组会吃掉 shell 行编辑键的组合** ——
  前缀键的问题以另一种形式回来了。

  **建议：Linux 端把默认命名空间从 `Alt` 换到 `Super`（Win 键）。**
  终端应用不使用 `Super`，它在 Linux 上是 `Cmd` 的等价物。
  代价是可能与桌面环境的全局快捷键冲突（需可配置），但这远比吃掉 `Alt+D` 轻。

这条同时是"macOS 领先一个阶段"之外、**又一个 macOS 应当先行的结构性理由**。

### 2.7 多路复用的两个维度（本轮新增的框架，很有用）

多路复用器实际提供两种彼此独立的能力：

| 维度 | 服务对象 | 内容 | 谁已经解决了 |
|---|---|---|---|
| **① 持久性** | 机器 | 进程一直跑、断开重连、重启恢复 | **tmux / Herdr 已完全解决**，Muxterm 不应重做 |
| **② 结构与注意力** | 人 | 每个位置有稳定、已知的含义；哪里需要我 | **基本无人解决** |

维度 ② 的关键证据是重度用户的实际用法（如 opencode 的 Dax）：
机器上的 tmux 常年不关，**每个 tab 做什么非常清楚、永远不动**。

> 价值不在"会话活着"，而在"**每个位置的含义是稳定的**"。**结构本身就是界面。**

**由此得到一条应当贯穿全产品的纪律：**

> ### 位置即记忆。任何会自动重排的东西，都在销毁用户已经建立的空间记忆。

这条纪律的直接推论（其中第一条推翻了本文档 §B.4 早先的写法）：

1. **工作区列表按固定顺序（创建序 / 用户手动排序），绝不按"最近使用"自动重排。**
   "最近使用"只允许影响**光标默认落点**，永远不允许影响**顺序**。
2. window / pane 的位置不因状态、输出、活跃度而调整。
3. 状态（`blocked` / `done`）只以**行内标记**呈现，只有「待处理」tab 才按 attention 排序 ——
   因为那个 tab 的存在意义就是"按紧急程度排"，用户不会去记它的位置。
4. tab 顺序固定、永不动态增删（已在 §B.2 规则 4 细则 2 写明，此处是它的理论依据）。

**这也把「工作区模板」从便利功能提升为机制。**
`twork` 铺出的 Monitor / Workstation / Playground 不是"省几条命令"，
而是**让每个项目的工作区拥有同一个已知形状**。形状统一之后会解锁一件目前没人做的事：

> **跨工作区的同名位置导航** —— 若所有项目都有 `Monitor` 窗口，
> "跳到当前工作区的 Monitor"在任何项目里都成立，"列出所有工作区的 Monitor"也变得有意义。

这是维度 ② 真正开始产生复利的地方。（先记为想法，不是当前承诺。）

### 2.8 "Muxterm 首先是 terminal GUI"——把竞品变成供给

本轮由项目负责人提出的一次定位反转，**它比本文档前面给出的位置更强，应当采纳为最终身份**：

> **Muxterm 首先是一个 terminal GUI。多路复用器是它的供给侧，不是它的竞争对手。**

前几轮把 emux / rmux / psmux / Zellij 当作"这个空白已经被填了"的证据（用于劝阻 Windows 方向）。
在"Muxterm 是多路复用器"的假设下这是对的；但在"Muxterm 是 GUI 客户端"的假设下**结论反过来**：

> **多路复用器越多、越活跃，一个好的原生 GUI 客户端就越值钱** ——
> 因为它们**没有一个**会去做原生 GUI。TUI-first 是它们的身份，不是它们的阶段。

历史类比就在眼前：**iTerm2 本身就是一个客户端，不是多路复用器。**
它从未实现过 session 持久化，它只是把 `tmux -CC` 当作线协议来消费 —— 然后成了 macOS 的默认终端。

**这个身份还解释了为什么前面所有的边界都是对的**：不做 agent 编排、不做手机端、
不做任务看板、不自研终端内核、不自研 SSH 认证 —— 因为**客户端的本分是消费别人的能力，并把它呈现得无可挑剔**。

#### ⚠️ 护栏：一条决定"要不要接这个 Runtime"的判据

"可以有更多 runtime"如果没有判据，会立刻退化成适配器跑步机 ——
每出现一个新多路复用器就欠一笔集成债，而用户一天也不会多得到什么。判据只有一条：

> ### 一个新 Runtime，只有当它能带来 **tmux 给不了的能力**时才值得接。
> ### 否则它只是又一个适配器成本。

按这条判据给生态分层：

| 层 | 例子 | 集成成本 | 是否值得 |
|---|---|---|---|
| **① 说 `tmux -CC` 的** | [psmux](https://github.com/psmux/psmux)（明确做成 `tmux -CC` 的 drop-in 线协议替身，为的就是对接 iTerm2） | **≈ 0，现有 TmuxRuntime 直接吃** | ✅ 白拿。Windows 也顺带覆盖了 |
| **② 有 tmux 给不了的能力** | **Herdr**（agent 状态、`working`/`blocked`/`done` 汇总、第三方 bridge API） | 一个专用适配器 | ✅ 唯一值得单独投入的一类 |
| **③ 只是"另一个 tmux"** | emux（自有 length-prefixed JSON IPC，tmux 兼容层还在 TODO）、rmux（命令级兼容，未见 `-CC`）、Zellij | 各欠一个适配器 | ❌ 不接。用户一天也不会多得到什么 |

**推论：Windows 的结论不变，但理由变了。**
不再是"空白已被别人填了所以别去"，而是：
**psmux 这类 `-CC` 兼容实现出现之后，Windows 上的多路复用能力会自己送上门 ——
Muxterm 该做的只有 Windows GUI 前端，而那是第四个前端，仍然应当排在最后。**

#### 这个身份把 Core Protocol 从"内部抽象"升格为"最有价值的资产"

如果 Muxterm 是 N 个 Runtime 的 GUI 客户端，那么 Core Protocol 就不再是内部整洁问题 ——
**它就是产品的边界，它的质量直接决定第 N+1 个 Runtime 是三天还是三个月。**

由此得到阶段 D 的一个重新定义：

> **接 HerdrRuntime 的真正交付物不是 agent 感知，而是"多 Runtime"这个论断的审计。**
>
> tmux 的语义有没有偷偷漏进 Core Protocol，只有第二个真实 Runtime 能验出来。
> **接得顺 = 论断成立；接得痛 = 在自称多 Runtime 之前，Core Protocol 还欠债。**

agent 状态只是这次审计的附赠品。

#### 关于自建 daemon：区分"聚合器"和"多路复用器"

项目负责人提出后期会补全自己的 daemon（可选项，也可以只是为了好玩）。
这件事**值得做，但必须先分清两种截然不同的 daemon**，因为其中一种会摧毁上面的整个身份：

| | daemon 作为**聚合器**（surface 的一部分） | daemon 作为**多路复用器**（Runtime 的一部分） |
|---|---|---|
| 职责 | 汇总所有 Runtime 的工作区状态；GUI 关掉时仍能回答"哪里需要人"；给 botmux 等上层一个只读出口 | 自己持有 pane、自己做 session/window/layout/attach |
| 与身份的关系 | ✅ **强化** —— 它是"注意力"这一维度在无 GUI 时的延伸 | ⚠️ **威胁** —— Muxterm 变成自己想托管的那类东西的竞争者 |
| 建议 | **这是阶段 E 的正解**，应当明确规划 | 限定为「本地 shell 的持久化」这一个用途，不要长成第四个多路复用器 |

换句话说：**让 daemon 回答"发生了什么"，不要让它回答"东西活在哪"。**
后者已经有 tmux 和 Herdr 了，而且它们做得比你好。

（"只是为了开心"是个人项目完全正当的理由 —— 唯一需要守住的是别让它悄悄变成主线。）

#### 身份的代价：渲染质量再没有借口

**多路复用器可以在渲染上平庸**（宿主终端负责渲染）；**terminal GUI 不可以。**
一旦身份是客户端，字体与连字、选择与复制手感、URL 识别、CJK/IME、scrollback 性能、
resize 行为、24-bit 色、鼠标上报 —— 这些不再是"基础项"，**它们就是产品本身**，
而对标线是 iTerm2 / Ghostty / kitty 立的。

`docs/macos-ui-research.md` 里"SwiftTerm 起步，必要时换 libghostty-vt + 自绘 Metal"的对冲是对的，
在这个身份下它的重要性还要再上调一档。

### 2.9 功能差距的真实形状（对标 iTerm2 / Ghostty / kitty，2026-08-14 核查）

"他们做了那么多，我们还差多少？"——先看他们**实际在更新什么**，再判断哪些是你的债。

**核查来源与时间：** kitty [changelog](https://sw.kovidgoyal.net/kitty/changelog/)（0.48.2，2026-07-30）、
Ghostty [1.3.0 release notes](https://ghostty.org/docs/install/release-notes/1-3-0)（2026-03-09）、
iTerm2 [downloads](https://iterm2.com/downloads.html)（3.6.11，2026-06-02）。核查于 2026-08-14 00:2x CST。

他们持续投入的东西可以归为四类，**其中三类不是 Muxterm 的债**：

| 类别 | 他们在做什么 | 是 Muxterm 的债吗 |
|---|---|---|
| **A. 终端仿真正确性与协议** | kitty 自创 graphics / keyboard / text-sizing / 多光标 / 拖放协议；OSC 133、OSC 8、mouse 上报的无尽边界 | **大部分不是** —— 外包给 SwiftTerm / VTE |
| **B. 平台集成与渲染** | kitty 0.48 的详细 changelog 几乎全是 Wayland 合成器差异、分数缩放、macOS 窗口层级、字体对齐；Ghostty 的可变字体、IME | **大部分不是** —— 同上，但**上限受制于 SwiftTerm** |
| **C. 自成体系的功能生态** | iTerm2 3.6：AI Chat、**浏览器 profile**、密码管理器（1Password/Bitwarden/Keeper）、session 归档、triggers、进度条；kitty：kittens（choose-files/diff/hints/notify）、quake 终端、垂直 tab | **明确不做** —— 这正是"客户端身份"排除掉的东西 |
| **D. 性能** | kitty 的 SIMD 解析（2x）、Ghostty 的并发搜索线程 | 你已实测占用低，暂无债 |

> **关键结论：那种"他们做了好多"的观感，绝大部分来自 C 类 —— 而 C 类是你已经明确决定不做的。**
> 真正会限制你的是 A/B，而 A/B 你不通过"加功能"解决，只通过**换引擎**解决。
> 所以真实问题不是"Muxterm 还差多少功能"，而是"**SwiftTerm 还差多少**"——
> 这把压力精确地压到 `macos-ui-research.md` 已经写好的那个 libghostty-vt 对冲上。

#### ⚠️ 发现 1：注意力的**原语**正在收敛，但**聚合**没人做

Ghostty 1.3.0 已经发布 **Command Finished Notifications**：

```
notify-on-command-finish = unfocused      # never / unfocused / always
notify-on-command-finish-action = no-bell,notify
notify-on-command-finish-after = 30s      # 最短时长门槛
```

三个设计细节值得直接抄：**只在未聚焦时通知**、**有最短时长门槛**、**bell 与桌面通知可分别开关**。
这三条正是本文档 §B.2 说的"零误报干扰"的具体实现方式。

但更重要的是战略含义：

> **每个终端都会有"这个 session 的命令跑完了"的通知 —— 这个原语正在变成标配，不是差异化。**
> 没有任何一个终端能回答的是：**"我 40 个工作区、5 台机器，哪一个在等我？"**
>
> 因此阶段 B 的产物必须是**聚合体**，而不是 per-pane 通知。
> 如果做成"这个 pane 的命令跑完了就弹一下"，那是在重造 Ghostty 已有的东西。

#### ⚠️ 发现 2：OSC 133 是比 BEL 更好的信号 —— 它让"两态"升级为"三态"且不需要启发式

§B.3 曾建议"先只做 `working` / `needs-you` 两态，别用启发式区分 `blocked` 和 `done`"。
**这条建议在引入 OSC 133 之后可以放宽**（Ghostty 的实现已经验证了这条路）：

| 信号 | 覆盖的场景 | 得到的状态 |
|---|---|---|
| **OSC 133**（语义提示符：命令开始 / 结束 + 退出码） | build、test、脚本等**普通命令** | `working` → `done`（**精确，无启发式**） |
| **BEL / OSC 9 / 777 / 1337** | **agent**（一条长命令，133 判不出内部状态） | `blocked`（它主动响铃要人） |

两者**互补而非二选一**，合起来恰好覆盖了两种真实场景。
Fish 4.1+ 与 Nushell 0.111+ 原生发 OSC 133，其余 shell 靠 shell integration 注入。

顺带：OSC 133 还免费带来"跳到上一个/下一个提示符"和"复制上一条命令的输出"——
这两个都是重度终端用户的高频操作，且天然属于 §4.1 的"工作区导航"。

#### ⚠️ 发现 3：一条应当今天就自查的安全问题

Ghostty 1.3.0 修复了 **CVE-2026-26982**：

> 粘贴或拖放的文本中若含控制字符（如 `0x03` = Ctrl+C），可能在某些 shell 环境下**执行任意命令**。

**Muxterm 有粘贴、且计划做拖放投递（阶段 E），因此同一条攻击面成立。**
应当自查：粘贴路径是否过滤/转义控制字符、是否使用 bracketed paste、多行粘贴是否有确认。
这不是功能，是**安全债**，且成本很低。

#### 发现 4：`-CC` 集成的长尾，iTerm2 做了 13 年还在修

iTerm2 3.6.x 的 changelog 里仍有：

- *"Fixed a bug where tabs would switch unexpectedly in tmux integration"*
- *"Fix a bug where italics in tmux integration were displayed as reverse video when TERM contains 'tmux'"*

你的 `docs/bugfix-log.md` 里那些（tmux < 3.2 跳过颜色上报、后台 tab 布局事件导致 htop 抖动）**属于同一类**。

> **结论：这类 bug 不会收敛到零，应当把它当作常态成本预算，而不是"快修完了"的阶段。**
> 这也再次说明测试基建（真机 tmux/SSH 回归）的价值高于新功能。

#### 所以真实的剩余清单很短

与项目负责人自评一致（配置页、QuickConnect、终端优化），补充几条被漏掉的"日常终端不可缺项"：

| 项 | 类别 | 说明 |
|---|---|---|
| 配置界面 | 已识别 | 现在只有 TOML；`preferences` 在 Linux 端还是个 label |
| QuickConnect 完整化 | 已识别 | 见 §B.2 规则 4 的分 tab 设计 |
| 单 pane 查找 | 终端基础 | 直接用 SwiftTerm 自带 |
| **选择/复制手感** | 终端基础 | 双击选词、三击选行、矩形选择 —— 这是"客户端身份"下最不能含糊的一项 |
| **URL / 文件路径识别与点击** | 终端基础 | 高频，且是 agent 输出的主要消费方式 |
| **IME / CJK 输入与宽字符** | 终端基础 | 中文用户，必须无瑕疵 |
| 拖拽文件入终端插入路径 | 终端基础 | 同时是阶段 E 投递桥的前身 |
| **粘贴安全（CVE-2026-26982 类）** | **安全** | 见发现 3 |
| OSC 133 支持 | 阶段 B 的输入 | 见发现 2；顺带解锁提示符跳转 |
| 鼠标上报 | 终端基础 | TUI 应用依赖 |

**不做清单（对标出来的，明确划掉）：** AI Chat、内置浏览器、密码管理器、session 归档、
triggers/profiles 体系、kittens 式的附带工具集、自创终端协议。

## 2.10 2026 的终端热潮：三个必须直面的结构性事实

> 核查于 2026-08-14 00:4x CST。来源见各条末尾。

### 事实一：融资最多的终端公司，把终端层免费送掉了

**Warp**（2020 年成立，累计融资 $139M，2026 年 6 月 $60M 新一轮，Battery Ventures 领投）
在 **2026 年 4 月把客户端以 AGPL 开源**，同时把公司重心移到 **Oz —— 云端 agent 编排平台**，
自称从"终端"变成"Agentic Development Environment"乃至"software factory"。
创始人 Zach Lloyd 的原话大意是：**agent 采用的瓶颈不是终端 UX，是编排。**

外部分析给出了更冷的解读：

> *"如果你守不住一个三家万亿级公司正在免费送的层，你不会在那层加倍下注。
> 你会爬到一个他们还没商品化的层。"* —— [ClawBlog](https://clawblog.com/warp-software-factory-execution-layer-consolidation)

**这条对 Muxterm 意味着两件方向相反的事，两件都要认：**

| 读法 | 内容 |
|---|---|
| ❌ **坏消息** | 终端客户端层**没有商业价值**。指望 Muxterm 变成生意，方向上就是错的。 |
| ✅ **好消息** | **商品化对个人开源工具是纯利好。** Warp 必须爬升是因为 $139M 要求护城河；Muxterm 没有这个义务。而 Warp 爬走之后，终端客户端层**设计能力最强的对手主动腾空了**。 |

更重要的是：**Warp 爬去的地方（云端编排、fleet、治理、software factory）恰好是 §2.2 明确划掉的**。
它没有跟你抢，它离开了你所在的位置。

> **结论：Warp 的转身不是对 Muxterm 的否定，是对"终端客户端能不能撑起一家风投公司"的否定。**
> 这两件事完全不同，别搞混。

### 事实二：「哪个在等我」是 2026 最拥挤的赛道 —— 而这正是阶段 B

这条必须说得很直白：**你计划作为差异化的那个功能，现在有二十几个工具在做。**

HN 上一个同类项目讨论串里，被点赞最多的建工具动机，一字不差就是阶段 B 的问题陈述：

> *"tmux 不会显示 agent 状态，也不会在某个需要输入时通知你。"*
> —— [HN 49109559](https://news.ycombinator.com/item?id=49107749)

同一赛道的部分名单：

| 形态 | 代表 | 说明 |
|---|---|---|
| **macOS GUI 编排器** | [Conductor](https://conductor.build/)（Melty Labs，YC S24，$22M A 轮）、Pane、Nimbalyst | worktree 隔离 + diff 审查 + 合并 |
| **tmux TUI 管理器** | [Claude Squad](https://github.com/smtg-ai/claude-squad)、[agent-manager](https://github.com/YoanWai/agent-manager)、agent-deck、claude-tmux、tmux-agent-switcher | 状态列表 + worktree |
| **看板 / 编排** | Vibe Kanban、Emdash、Superset、Parallel Code | **Vibe Kanban 母公司 bloop 已于 2026-04-10 关停**，转社区维护 |

同一个讨论串里也有这样的评论：*"这类东西有一打，除了几个主观取舍之外基本没区别。"*

**但穿透下去，有一条结构性区别是真的，而且只有 Muxterm 站在那一侧：**

> **它们全都是 agent-scoped、git-scoped、单机的。**
> 词汇表出卖了它们：worktree 隔离、diff 审查、合并/PR、成本追踪、看板。
> **它们是"碰巧跑在终端里的 git-centric agent 编排器"。**
>
> **Muxterm 是 process-scoped、machine-scoped 的。**
> 它不关心你跑的是 agent、`make`、`tail -f`、还是 ssh 到生产机上的 psql。

三条具体的、可验证的分野：

1. **跨机器。整个名单里没有一个做这件事。** Conductor 只管你 Mac 上的 worktree；
   Claude Squad / agent-manager 只管**本机那一个 tmux server**。
   "我在 3 台开发机上跑着 agent，哪台在等我" —— **今天无人回答。**
   而 Muxterm 的 SSH transport 天然覆盖它。

2. **不是"第二个住处"。** agent-manager 作者自己的辩护词恰好暴露了 TUI 的软肋：
   *"agent 本来就住在终端里，所以这个管理器是一个**视图**，而不是第二个住处。"*
   —— 但它**仍然是**：你在终端里干活，然后打开另一个 TUI，它占屏、有自己的键位、你得离开手头的事去看它。
   **Muxterm 不是终端上的一个视图，它就是那个终端。** 红点不需要你打开任何东西，
   Dock badge 在 Muxterm 没被聚焦时照样工作。这是 §2.6 那个论证，现在有真实市场验证了。

3. **状态检测对 Muxterm 近乎免费，对它们不是。**
   agent-manager 是靠**定时 `tmux capture-pane` + TOML 里配的正则**读状态。
   而 **Muxterm 为了渲染，本来就持有每个 pane 的完整屏幕内容** ——
   拿最后一行非空文本做一次正则匹配，成本约等于零。**这是"身为终端"带来的结构性成本优势。**

#### 由此得到一条重要的实现修正：状态检测不要绑定 agent 名单

名单里每个工具都硬编码支持的 agent 列表（Claude Code / Codex / Gemini / Amp / OpenCode / Grok…）。
**那是一条跑步机：出一个新 agent，欠一笔集成债。**

正确做法与"Muxterm 是终端"的身份一致：**把 `blocked` 定义为通用行为，不是 agent 属性。**
`apt install` 等 y/n 和 Claude 等确认，**是同一件事**。
三路信号合流，且**全部与厂商无关**：

| 信号 | 来源 | 用户可扩展性 |
|---|---|---|
| OSC 133 | 命令开始/结束（见 §2.9 发现 2） | 无需配置 |
| BEL / OSC 9·777·1337 | 进程主动求关注 | 无需配置 |
| **末行正则** | 用户在 TOML 里自己加一条 | **完全开放** |

第三条是关键：**把扩展权交给用户**，Muxterm 自己一个 agent 名字都不用认识。

### 事实三：潮水方向对，但所有人都知道了

- Claude Code 现在贡献了公开 GitHub 提交的约 4%，每天约 13.5 万次
- 69% 的开发者全天保持终端开启
- Ghostty macOS 版约每周 100 万次下载，并已转为非营利以避免被收购
- Cline 从 VS Code 插件重建为 CLI，理由是：*"当工作是自动补全时，IDE 侧边栏是个好归宿。但工作已经变了。"*

（以上数字来自 [Hyperbliss](https://hyperbliss.tech/blog/2026.04.04_terminal-renaissance/) 与
[jiaweing.com](https://jiaweing.com/blog/the-gui-lost) 等二手综述，**非一手披露，量级参考即可**。）

还有一条与技术路线直接相关：多篇分析都提到**生态可能收敛到 libghostty 这类共享 VT 库**上。
如果这是真的，`macos-ui-research.md` 里那个 libghostty-vt 对冲就**不只是备胎，而是顺流** ——
理由从"SwiftTerm 可能不够用"升级为"不必自己维护终端正确性这条无底线"。**建议把它的评估时点提前。**

### 2.10.5 由此得到的位置判断

Muxterm 处在一个**被两面夹逼、但确实存在的夹缝**：

```
    ┌───────────────────────────────────────────────┐
    │  上方：agent 编排器（Conductor / Warp Oz / …） │
    │  会聚合 —— 但只聚合 agent、只围绕 git、        │
    │  只在单机，且是"第二个住处"                    │
    └───────────────────────────────────────────────┘
                          ↓ 向下伸
    ┌───────────────────────────────────────────────┐
    │  Muxterm：像编排器一样聚合，但它就是终端，     │
    │  且 process / machine / runtime 无关           │
    └───────────────────────────────────────────────┘
                          ↑ 向上伸
    ┌───────────────────────────────────────────────┐
    │  下方：终端（Ghostty 1.3 命令完成通知）       │
    │  会通知 —— 但只在单 session、单窗口、单机      │
    └───────────────────────────────────────────────┘
```

**夹缝会不会被合上？** 会，如果：Ghostty 加多路复用 + 跨机聚合（不符合它 do-one-thing-well 的性格），
或某个编排器长成一个真正的终端（要付 §2.9 A/B 两类的全部代价）。**两条都不便宜，但都不是不可能。**

> **所以时间是真变量。** 但不必恐慌：Vibe Kanban 的公司已经死了，那一打工具大部分会死。
> 活下来的会是**身份最耐久的**那些。
> "一个 tmux 上的 TUI 包装器"不是耐久身份；**"我就是你天天开着的那个终端"是。**

## 2.11 Superlogical：迄今最严重的威胁，同时是最强的验证

> **2026-07-29 成立，距本次评审 16 天。核查于 2026-08-14 00:5x CST。**
> 来源：[Mitchell Hashimoto 本人公告](https://mitchellh.com/writing/superlogical)、
> [superlogical.com](https://www.superlogical.com/)、
> [The Register 2026-07-31](https://www.theregister.com/devops/2026/07/31/dev-who-gave-hashicorp-its-name-returns-with-a-faster-terminal-multiplexer/5281970)。

**事实（已核实）：**

- Ghostty 作者、HashiCorp 联合创始人 **Mitchell Hashimoto 创办 Superlogical**，已融资（金额未披露）
- **首个产品就是终端多路复用器**，服务端持久 session，关掉应用、换设备都能接回原处
- **构建在 libghostty 之上**，走 MIT 组件并承诺回馈上游
- **同时提供 Web + 原生 macOS / iOS 客户端**，live session 共享内建
- 明确要解决的是：*"现有工具最常见的痛点 —— 让 **scrollback、选择、滚动** 都原生地正常工作"*
- 愿景是"**a multiplexer for all work**"：本地开发、远程访问、coding agents、后台任务、
  生产应用、线上调试、沙箱、共享终端、事故响应、**人与机器**、操作历史、多人协作
- 现状：**只有 waitlist**，无产品、无定价、无发布日期

### 为什么这是迄今最严重的威胁

| # | 原因 |
|---|---|
| 1 | **它是垂直整合的**：多路复用器 **+** 原生客户端一起做。它不在 Muxterm 的下游，它**同时占据了 Muxterm 的位置和它的供应商位置**。 |
| 2 | **它的宣传语就是 Muxterm 的宣传语**："让 scrollback、选择、滚动原生地正常工作" —— 这**逐字**是 Muxterm 相对 tmux 的价值主张。 |
| 3 | **终端质量从第一天起就是顶配**（libghostty），而这恰是 Muxterm 最弱的一环（SwiftTerm）。 |
| 4 | **分发与信誉的量级差**：Ghostty 每周百万次下载的作者。 |
| 5 | 它的 scope 里**明确列了 coding agents 和 operational history** —— 即注意力/感知那一层。 |

### 但它同时是这份文档能拿到的最强验证

> **世界上最懂终端的人之一，看着同一片地形，得出了和你一样的结论：**
> **多路复用器才是关键，持久化才是关键，现有的那些不够好。**

你不是在想象一个不存在的问题。你的方向判断刚刚被以最高规格背书了。

### 关键分野：**它要你搬家，Muxterm 要你什么都不用搬**

这是唯一真正结构性、且不随执行力变化的区别：

| | Superlogical | Muxterm |
|---|---|---|
| **前提** | 你**改用**它的多路复用器 | 你**继续用**你已经在用的东西 |
| **迁移成本** | 40 个 tmux session、`twork` 脚本、所有肌肉记忆 | **零** |
| **身份** | 一个新的运行时 + 它自己的客户端 | **任何运行时的客户端** |
| **商业形态** | 服务端可收费（团队 / 共享 / 事故响应 / 生产） | 无商业形态，也不需要 |

Superlogical 必须为一个**市场**建构，因此会向中位数和可收费处优化（团队、共享、合规、生产）。
它**不可能**为"worktree bare 大仓 + tmux + 40 个 session + 纯键盘 + 不要侧边栏"优化 ——
这不是它的失败，是结构差异。**这正是你试遍所有产品最后还是回到自写 `twork` 的原因。**

### 由此改变的三个决定

**① libghostty 的评估从"备胎"升级为最高杠杆的技术决策。**
§2.10 说生态可能收敛到 libghostty；Superlogical 的选择基本坐实了这件事。
如果 Muxterm 也走 libghostty，它就**与最强对手处在同一技术生态内**，白拿上游改进，
并且天然是"未来任何 libghostty 系运行时"的合格客户端。
**这条的优先级现在高于本文档里除阶段 B 之外的一切。**

**② "将来自己写个 daemon" 这个念头应当彻底封存。**
之前把它列为"可选项、图个开心"。现在的对手是一支拿了钱、专职、由基础设施老兵组成的团队，
在做**同一个东西**。LocalBackend 应当严格锁死在"Windows / 无 tmux 的本地场景"，
**永远不要向"我们自己的多路复用器"生长**。这不是胆怯，是把力气放在唯一能赢的地方。

**③ 要盯的不是"它会不会比我更懂我的工作流"（不会），而是"它会不会开放客户端协议"。**
Hashimoto 说这套设计要求 *"每个接入的客户端都是非常聪明、高度合规的客户端"*，
这**暗示存在一份协议**。若协议开放 → Superlogical 变成 Muxterm 的又一个 Runtime，且**完全符合 §2.8 的接入判据**
（它给得出 tmux 给不了的东西：跨设备接回、内建共享）。
若不开放 → 它就是个封闭的垂直产品，与 Muxterm 各走各路。
**这一条是未来 6-12 个月唯一值得持续跟踪的外部变量。**

### 2.11.5 澄清一个容易混淆的点：Superlogical 不是"卖服务器"

很容易把 Superlogical 的"服务端"与 Codex 云端、Cursor web 后台 agent 归为一路。
**这是两个不同的层，混淆它们会得出错误的战略结论。**

| 层 | 卖什么 | 代表 | 你的进程跑在谁的机器上 |
|---|---|---|---|
| **算力托管层** | **机器本身** | Codex cloud、Cursor 后台 agent / web、Devin、Jules | **他们的** |
| **会话 / 连接层** | 环境之上的**持久会话与连通性** | **Superlogical**、Tailscale 形态 | **你自己的** |

证据就在 Superlogical 首页：它说工作 *"横跨本地机器、远程主机、沙箱、服务与生产系统"*，
而缺失的是 *"一个围绕工作本身的持久 session —— **能横跨应用与环境**的那种"*。
**多路复用器按定义就是复用"跑在别处的进程"的流，它不提供那个"别处"。**

> **所以 Superlogical 是 Tailscale 形状，不是 AWS 形状。**

**这个澄清让威胁的形状变了，而且是往更严重的方向：**
它不在算力层跟 Codex 抢，**它就站在 Muxterm 所在的那一层**——会话层。重合度比上一节说的还高。

**但同时也暴露了唯一的、价值观级的分野：**

> 会话层要做到"跨设备接回"和"与别人共享 live session"，
> **几乎必然需要一个托管控制面**（账号、中继、会合点），这也正是它的收费位置。
> **而 Muxterm 一个都不需要。**

**这恰好命中你描述的那批人：** dax 买裸金属、你跑家里的 5950X、你朋友把机器寄机房 ——
**三个人用行动表达了同一个偏好：我要自己拥有这台机器，不租，不要中间人。**
这批人恰恰最不可能接受"我的会话层跑在别人的控制面上"。

> **这不是功能之争，是"租"与"拥有"之争，而这两批人不重叠。**

### 2.11.6 最可能的结局：Superlogical 会成为供应商，而不是对手

Hashimoto 的职业生涯是 **open-core**：Vagrant、Terraform、Vault 全部开源，
商业化在协作与治理层（Terraform Cloud、HCP Vault）。他本人也说会有 *"沿途的 OSS 发布"*。
据此**最可能的形态**是：

```
开源、可自托管的多路复用器内核  ←── Muxterm 应当接的 Runtime（免费，且质量顶级）
        ＋
托管控制面：团队 / 共享 / 生产 / 事故响应  ←── 收费，且不是本产品用户的问题
```

若果真如此，对 Muxterm 是**净利好**：白得一个 libghostty 系、比 tmux 强的运行时，
而它收费的那半恰好是 §2.2 早就划掉的东西。

**因此跟踪变量应当收窄成一句：**

> ### OSS 内核里**包不包含客户端协议**？还是"好客户端"被留给付费产品？
> HashiCorp 的历史模式是**内核完全可用**。若沿用，Muxterm 赢。

#### 附：「他在 HashiCorp 亲眼见过这套动力学」具体指什么（时间线已核实 2026-08-14）

这套动力学有光明与阴暗两半，Hashimoto 从 2012 到 2023 年（CEO→CTO，共 11 年）全程在场：

**上半场 —— open-core 楔子的威力：**

| 层 | 免费开源（获客楔子） | 收费（组织层） |
|---|---|---|
| HashiCorp 产品 | Vagrant / Packer / Terraform / Vault / Consul / Nomad，全部 MPL 2.0 | Terraform Cloud / HCP / Enterprise：**团队协作、state 管理、治理、审计** |

规律：**单人用的那半必须免费且极好**，否则采用率起不来；钱在"多人一起用"的那一刻才出现
（协作、状态共享、权限、合规）。个人用户从头到尾不付费，也**不需要**付费。

**下半场 —— 同一模式的代价（他也全程目睹）：**

- **2023-08-10**：HashiCorp 把全线产品从 MPL 2.0 改为 **BUSL 1.1**（禁止竞争性商用）——
  上市公司增长压力最终传导到了许可证上（[官方公告](https://www.hashicorp.com/blog/hashicorp-adopts-business-source-license)）
- **2023-09**：社区立刻 fork 出 **OpenTofu**，捐入 Linux 基金会，MPL 2.0，drop-in 兼容
  （[OpenTofu 公告](https://opentofu.org/blog/opentofu-announces-fork-of-terraform/)）
- **2023-12**：Mitchell 离开自己创办的公司
- **2025-02-27**：IBM 以约 **$6.4B** 完成对 HashiCorp 的收购

**这解释了 Superlogical 的两个否则难以理解的动作：**
把 Ghostty **捐给联邦认可的非营利组织**（法律上锁死，任何公司包括他自己的都拿不走），
以及反复强调 Superlogical 只**消费** MIT 的 libghostty 且回馈上游。
**他在用结构性手段预防自己经历过的那场事故重演。**

> 对 Muxterm 的启示顺带记录：这也是为什么"Muxterm 不需要商业模式"是优势而非缺陷（§2.11.7）——
> BUSL 事故的根源是"开源资产上压着投资回报要求"。Muxterm 头上没有这个东西。

**另：本项目作者自己的公司（yaklang.io）运行的就是同一套模型** ——
安全工具开源免费，AI 服务与团队 ToB 收费。
这意味着对 Superlogical 商业行为的预判，出自**模型的运营者**而非旁观者，可信度应当上调。

### 2.11.7 一个反直觉的推论：这批用户无法被货币化 —— 这正是护城河

把上面几条合起来：

| 事实 | 推论 |
|---|---|
| AI 时代确实需要长期在线的大机器（你、dax、你朋友都是证据） | 市场在长大 ✅ |
| 但这批人的选择是**自己买机器**，不是**租别人的** | 他们**不会付订阅**——买机器就是为了不付 |
| 于是没有公司会专门为他们做客户端 | **因为在这里赚不到钱** |

> **Muxterm 的用户群，定义上就是"不可货币化"的那批人。**
> 这既是它**必须**开源免费的原因，**也是它几乎不会遇到正面竞争的原因** ——
> 商业公司不会来，而多数个人开发者做不到这个完成度。

这也给 §7 的风险表一个反面：真正的风险从来不是"被大厂碾压"，
而是**作者自己失去兴趣**。护城河是热情，不是技术。

### 2.11.8 他们为什么这么选：双重仿真接缝 —— 而 Muxterm 正坐在这条缝上

"数据都在 server 不就够了吗？tmux/herdr 就是这么设计的" —— 这个直觉基本对，
但**恰恰是"只在 server"造成了 tmux 那三个痛点**。要害不在数据放哪，在**线上格式**。

**tmux 的真实数据通路（双重仿真）：**

```
程序 → ANSI 字节
   ↓
① tmux server 解析 ANSI，维护自己的屏幕网格   ← tmux 本身就是一个完整的终端仿真器
   ↓
② tmux 把网格 重新序列化 回 ANSI            ← 有损、且是 1970 年代为电传打字机设计的格式
   ↓
③ 你的终端 再解析一次 ANSI，维护第二份网格
   ↓
④ 渲染
```

**串联了两个完整的终端仿真器，中间的线协议是 ANSI。** 由此推出的全部后果都能对上号：

| 现象 | 根因 |
|---|---|
| **滚动 / 选择 / scrollback 难用** | 历史**只在 server**。客户端手里没有数据，只能进 copy-mode —— 那是**服务端模式**，靠重绘整屏实现。所以无法原生滚动、无法原生选择。 |
| **富协议被吃掉** | 第 ② 步的重新序列化是有损的。图片、超链接、文字尺寸都得靠 passthrough 打洞。 |
| **慢** | 每次变更都要重解析 + 状态对账；resize 还要 reflow。 |
| **`TERM` 含 tmux 时斜体变反显、颜色上报要按版本跳过、后台 tab 布局事件让 htop 抖** | **全部是同一条缝的症状**（`docs/bugfix-log.md` 与 iTerm2 3.6.x changelog 里是同一类 bug）。 |

**Superlogical 的技术命题就是换掉线协议：** 服务端持有权威状态，
但下发的是**结构化状态**而不是 ANSI 字节流，客户端持有一份副本，
**本地**完成渲染、滚动、选择。这就是为什么他们要求
*"每个接入的客户端都是非常聪明、高度合规的客户端"* —— 客户端不再是哑的 ANSI 接收端，
**它是仿真器的另一半**。也正因如此，libghostty 是前提而不是选型偏好。

> **所以答案是：他们不是"把数据搬到 server"（本来就在），而是"把客户端从哑终端升级成状态副本"。**

**那为什么这需要一家公司？** 两个原因，都诚实：

1. **工程量确实要团队和数年** —— 协议 + 服务端 + Web/macOS/iOS 三个智能客户端。
   Hashimoto 原话就是"一个需要团队的 scope"。
2. **多路复用器本身当不了护城河**（tmux 免费、herdr 免费、Warp 把客户端也送了）。
   钱只能在别处，而首页已经写明在哪：**live 共享、multiplayer、事故响应、生产、操作历史** ——
   **每一条都是"多人/组织"特性，而多人特性既需要控制面，又卖得动。**

> **推论（对你有利）：单机那一半几乎必然免费且做到极好，因为那是获客楔子。**
> 向单个开发者收多路复用器的钱会掐死采用率，而他在 HashiCorp 亲眼见过这套动力学。

### ⚠️ 由此暴露的、Muxterm 自己的一个具体缺陷

**好消息：Muxterm 的架构已经站在正确的一侧。** 它通过 `%output` 拿到 pane 的**完整字节流**
（`tmux/backend.rs` 里甚至有回归测试断言"拼接后必须与真实字节流完全一致"），
并在 `protocol/terminal/emulate.rs` 里维护自己的屏幕与 scrollback ——
**这已经是"智能客户端"模型的雏形了。**

**坏消息：这个能力被两处限制卡死，且其中一处是 bug 级的。**

| 问题 | 位置 | 说明 |
|---|---|---|
| **配置项是死的** | `config.rs` 的 `[scrollback] lines` | **被解析、被单测覆盖，但全仓库无任何地方读取它** |
| **硬编码 1000 行** | `emulate.rs:660` `SCROLLBACK_MAX_LINES = 1000` | 与配置项完全脱钩 |
| **O(n) 淘汰** | `emulate.rs:492` `Vec::remove(0)` | 每滚一行搬一次整个数组，应为 `VecDeque` |

**为什么这件事的优先级比它看起来高得多：**

> **客户端 scrollback 是阶段 B（peek）与阶段 C（跨工作区搜索）共同的地基。**
> **搜不到你没存的东西。** 1000 行意味着搜索窗口大约只有几屏 ——
> 那会让阶段 C 在做完之后显得没用，而根因不在搜索实现，在这里。

**需要先定的一个决策：搜索与 peek 读的是哪一份 scrollback？**
Rust core 的 `emulate.rs`，还是 macOS 侧 SwiftTerm 自己的缓冲？
两份并存会导致"看到的"和"搜到的"不一致。**建议以 Rust core 为唯一事实源**，
理由是它跨平台、且是 Core Protocol 的一部分（与 §2.8 的身份一致）；
GUI 侧的缓冲只负责渲染。

## 2.12 从 Warp 的失败里提炼一条应当写死的判据

Warp 押的是"**让 AI 帮你写复杂命令**"。这个位置在 2024 年看起来很好，
到 2026 年被 Codex / Claude Code / OpenCode 整个吃掉 —— 因为**它的价值恰好坐在用户与模型智能之间，而那道缝隙必然合拢**。

把它一般化成一条判据，用来筛掉未来所有的功能提案：

> ### 模型变强时，这个功能是变得**更值钱**还是**更没用**？
> ### 只做前者。

| 功能 | 模型变强时 | 判定 |
|---|---|---|
| AI 补全命令 / 解释报错 | **更没用**（agent 直接就做了） | ❌ Warp 踩的就是这个 |
| 聚合"哪个工作区在等我" | **更值钱**（agent 更多、跑更久、并行更狠） | ✅ 阶段 B |
| 跨机器 / 跨工作区搜索 | **更值钱**（现场更多） | ✅ 阶段 C |
| 终端渲染质量、选择复制、IME | **中性**（永远值钱） | ✅ 基础 |
| 内建 AI Chat | **更没用** | ❌ |

**注意阶段 B 落在哪一格**：它感知的是**行为**（有人在等输入），不是**内容**（它在说什么）。
所以它**不与模型能力竞争，而是随模型能力增值**。这是 Muxterm 全部设计里最耐久的一块，
也解释了为什么"不要解析 agent 输出、不要认 agent 名字"（§2.10）不只是省事，**是护城河本身**。

## 2.13 定位升级：远程 + 持久不是特性，是前提

本文档此前把"跨机器"当成一个**能力**。这个判断偏保守。正确的说法是：

> **在 agent 时代，"工作跑在一台不会睡的机器上"是结构性必然，不是个人偏好。**

论证很硬，且不依赖任何品味判断：

1. agent 的任务是**长时间自主运行**（几十分钟到几小时）
2. 本地客户端**总会停**：合盖、休眠、重启、换地方、断网
3. 因此**持久化 + 远程**不是优化，是这类工作能不能成立的前提
4. 而**编排器那一打工具全部是本地 Mac App**（Conductor、Pane、Nimbalyst），
   Cursor / Codex 的侧边栏也是本地 —— **它们在形态上就无法承接第 3 条**

**这一点上有两个独立的强背书：**

- **Superlogical 得出了同一结论** —— 服务端、持久、跨设备接回（§2.11）
- **OpenCode 的 dax 等远程开发实践者**在走同一条路

而 Muxterm 的架构**已经**站在正确的一侧：tmux 在远端跑，SSH transport，客户端只是窗口。

**因此定位句里"跨机器"应当从修饰语提升为主语：**

> **你的工作跑在一台永不休眠的机器上；Muxterm 是望向它的那扇窗 ——**
> **一个窗口装下全部在飞的工作区，并告诉你哪一个在等你。**

顺带解释了一件事：为什么 IDE 那套形态（左 AI 列表 / 中对话 / 右 git·terminal·file·web）
对这个用户不够用 —— **它把终端降级成第四个 tab**。
当你的主对象是"一个正在跑的进程"而不是"一个文件"时，这个层级是反的。
Muxterm 的形态正好翻过来：**终端是整个窗口，其余一切是临时浮层**（§B.4 的"一个终端 + 一个面板"）。
两种形态各自成立，因为**主对象不同**；但服务于"进程是主对象"的那一侧，今天几乎空着。

## 2.14 终局形态与长期方向（2026-08-14 四轮，综合全部讨论）

前面各节回答的是"是什么、不是什么、对手是谁"。本节回答两个剩下的问题：
**做完了长什么样（形态），以及之后往哪走（方向）。**

### 2.14.1 终局形态：一扇窗、一个面板、一枚红点

**用户可见的表面只有三样东西。能数得出第四样，就是设计错了。**

**① 一扇窗 —— 窗口就是终端。**

- 整个窗口就是终端内容。tab 条即**工作区**列表（不是 tmux window 列表），固定顺序（位置即记忆），
  状态以内联小标记呈现（`●` 等我 / `✓` 刚完成 / 安静 = 在跑或空闲）。
- 没有侧边栏、没有工具栏、没有常驻状态区。IDE 把终端降级成第四个 tab；
  Muxterm 把除终端外的一切降级成浮层。

**② 一个面板 —— 唯一的控制面。**

`Cmd-P` 唤出，三个 tab（Tab/Shift-Tab 轮换，输入随 tab 保留）：

| Tab | 回答的问题 | Enter 的语义 |
|---|---|---|
| **Workspaces** | 去哪 | 切换（默认选中上一个工作区 → `Cmd-P Enter` = 秒回） |
| **Attention** | 谁在等我 | 跳到那个 pane；**行内即可 peek + 一行答复**（§B.4 修正） |
| **Search** | 那个东西在哪 | 跳到命中坐标并还原滚动位置 |

面板还吞掉两件事：**建区**（`twork` 内化为模板建区 —— 输入不存在的名字 → 按模板创建）与**连接**
（工作区列出**所有已知**的，未连接的选中即连 —— "一键可达"而非"永远连着"）。

**③ 一枚红点 —— 唯一的常驻注意力表面。**

手机通知模型（§B.1）的完整闭环：状态栏/标题栏角落红点 + Dock badge + （签名后）系统通知 +
blocked 专属提示音。红点只为"**卡在我身上**"亮。

**③.5 新增一条形态级决定：窗口可关，感知常驻。**

手机收通知不需要 App 开着 —— 这个模型补完整就是：

> Muxterm 以**菜单栏项**常驻。窗口关闭时，对已注册工作区保持 **control-mode 轻连接**
> （纯文本事件流，带宽与 CPU 成本接近零），红点 / Dock badge / 通知照常工作，点击即回窗口。

这不引入任何新进程/daemon —— App 本身就是那个进程。它也回答了 warm connection pool 的最终归宿：
**渲染可以懒，感知必须常驻**。"全部保持渲染"太贵，"全部保持监听"很便宜。

> **✅ 已批复（2026-08-14 02:1x，项目负责人）："窗口可关，保持到状态栏里，很符合常识。"**
> 至此 §2.14/§2.15 的全部悬决事项关闭。随批复补两条实现细节：
> ① **全局热键**唤起窗口/面板（与常驻配套，iTerm2 Hotkey Window 的先例）；
> ② **重启恢复**：App 重启后恢复工作区 tab 集合与窗口位置（布局记忆是客户端状态，按工作区身份持久化）。

**④ 看不见的一半（架构终态）：**

```
GUI（AppKit / GTK4，各平台独立，只做渲染与输入）
   │
Core Protocol（Rust，跨平台唯一事实源）
   ├─ 工作区注册表：workspace = (runtime, host, session)，位置只是属性
   ├─ 每 pane 状态机：working / done / blocked（OSC 133 + BEL + 用户正则，§2.10）
   ├─ 每 pane 客户端 scrollback 副本（§2.11.8 —— peek/搜索/选择的共同地基）
   └─ Runtime 适配器：tmux ✅ / local / herdr / superlogical(若协议开放)
   │
只读状态出口：`muxterm status --json` + socket（阶段 E —— botmux、脚本、状态栏消费）
```

**⑤ 多机同构：** macOS 与 Linux 同一形态、同一 TOML、同一键位；配置同步走 dotfiles/git，不走云。
这是"拥有自己机器的人"的同步方式（§2.11.7 的价值观贯彻到底）。

### 2.14.2 「做完」的定义 —— 这个产品以完成为荣

> **A（日用）+ B（可见性）+ C（搜索）= 1.0。**
> 对一个人证明全部命题。D（herdr）/E（出口）是扩展，不是完成条件。

这个产品的榜样是 tmux 而不是 Chrome：**它应当趋于完成，而不是持续膨胀。**
1.0 之后的增长轴是：更多 Runtime 适配器（社区可写）、更好的渲染引擎（libghostty-vt）、
更多平台同构（Linux 追平、Windows 视个人需要）—— **全部是深度与质量，没有一条是新品类功能。**

## 2.15 定案之后的开放设计题与新点子（四轮，2026-08-14 01:5x CST）

### 2.15.1 设计题 ①：红点何时熄灭（注意力的确认语义）—— 阶段 B 的最后一块设计

> **✅ 已批复（2026-08-14 02:0x，项目负责人）：按下述规则保留。**

前面定了红点何时**亮**（blocked at me），但从未定过何时**灭**。
这是通知系统的已读/未读模型 —— 定错了徽标就会说谎（挂着过期项 → 麻木；过早清除 → 漏事）。

**建议规则（全自动，绝不引入手动"标记已读"）：**

| 状态 | 熄灭条件 | 原因 |
|---|---|---|
| `blocked` | **该 pane 收到用户输入**，或阻塞状态自行消失（提示符走了 / 进程恢复输出） | "已回应"才算处理，**切过去看一眼不算** |
| `done` | **该 pane 被看见**（成为可见 pane），类似未读消息 | "已看见"即确认 |

三条边界纪律：

1. **聚焦工作区 ≠ 确认**。blocked 的 pane 若在该工作区的后台 tab 里，切到工作区不清除它 ——
   只有对**那个 pane** 输入才清除。否则徽标会在你没处理时熄灭（说谎）。
2. **错误清除允许自愈**：若清早了，下一次 BEL / 正则命中会重新点亮。宁可重亮，不可漏亮。
3. **手动操作只有一个**：面板里对单项 `静音 1 小时`（针对确实想晾着的 pane）。
   没有"全部已读"—— 一旦需要"全部已读"，说明检测的信噪比坏了，该修检测，不是加按钮。

### 2.15.2 设计题 ②：断线必须无聊（重连是日常路径，不是异常路径）

产品前提是"工作跑在永不休眠的机器上"（§2.13），那么**客户端这边每天都在断**：
合盖、睡眠唤醒、换网络、SSH 超时。**重连体验就是这个产品的日常真实感，其重要性不低于渲染。**
整个评审至今没有讨论过它。建议的完成标准：

| 场景 | 行为 |
|---|---|
| 断开瞬间 | **不弹任何东西**。最后已知画面保留展示，轻微降饱和 + 角落一行时间戳水印（"已断开 01:42 · 重连中"）。**因为有 scrollback 副本（§2.11.8），断开期间内容仍可滚动、选择、搜索** —— 副本从性能优化升格为韧性 UX |
| 重连 | 自动、指数退避有上限；快速恢复则全程无感；慢则维持水印，**永不弹模态框** |
| 唤醒风暴 | 20 个工作区不齐射重连：加抖动错峰，能复用 ControlMaster 就复用 |
| 断线期间的注意力 | 重连后查 tmux 的 `window_bell_flag` / `window_activity_flag` 并做一次 capture 补齐副本缺口，**重新推导状态 —— 承诺"断线不漏事"**（实现时验证 flag 在控制模式 attach 时的可得性） |

**验收测试就一条：合盖一小时，开盖 —— 一切如初、零对话框、错过的 bell 已在 Attention 列表里。**
这条建议进入公开发布的硬门禁（比多数功能更能留住目标用户群）。

> **✅ 已批复（2026-08-14 02:0x）：韧性方向确认，并追加两点 —— "考虑 mosh 那类增强传输"与"重连不许刷屏"。**
> 两点均已核实/落实如下。

**追加 A：增强传输的正确答案是 Eternal Terminal，不是 mosh（已核实，2026-08-14 02:0x CST）**

| 方案 | 与 `tmux -CC` 的兼容性 | 来源 |
|---|---|---|
| **mosh** | **根本不兼容，且官方无意支持。** mosh 自己就是终端仿真器（屏幕状态同步模型），不透传字节流，`DCS 1000p` 根本到不了客户端；实测"连上立刻断"。iTerm2 官方 wiki 原话：*"Don't use mosh for tmux integration... will cause you horrible agony."* | [mosh#640](https://github.com/mobile-shell/mosh/issues/640)、[mosh#1078](https://github.com/mobile-shell/mosh/issues/1078)、[iTerm2 wiki](https://gitlab.com/gnachman/iterm2/-/wikis/tmux-Integration-Best-Practices/diff?version_id=51f34e593dc24e474b2720d4d836b700867142ee) |
| **Eternal Terminal (ET)** | **明确支持。** ET 是"可断线重连、可漫游的可靠字节流"，官网专门写了 *"Works with tmux control center"*；ET 对比 mosh 时也点名 *"mosh does not support native scrolling nor tmux control mode (tmux -CC)"*。iTerm2 官方最佳实践直接推荐 `et -c="tmux -CC new -A -s main" host`。 | [eternalterminal.dev/howitworks](https://eternalterminal.dev/howitworks/)、[iTerm2 最佳实践](https://gitlab.com/gnachman/iterm2/-/wikis/tmux-Integration-Best-Practices/diff?version_id=51f34e593dc24e474b2720d4d836b700867142ee) |

**落点：** Transport 层加一个**可选的 ET 后端**（远端装了 `et` 就能用，配置里 per-host 开关），
Muxterm 自己的自动重连仍是默认路径（ET 是增强不是依赖）。
这与架构完全同构 —— SSH 是 Transport，ET 只是另一个 Transport，**一行协议代码都不用改**。

顺带一个有意思的注脚：mosh 的屏幕状态同步模型正是 Superlogical 的模型（§2.11.8）——
mosh 证明了结构化状态同步的威力，也证明了它与 ANSI 字节流协议（`-CC`）天然互斥。
**预测回显仍维持 v1 不做**（§2.15.6 第 4 条），等 Runtime 层出现结构化协议再由协议解决。

**追加 B：重连不许刷屏（渲染纪律）**

- 重连后的 catch-up 字节（capture 补齐 + 积压 `%output`）**静默喂给模型，模型收敛后一次渲染到位** ——
  过程绝不逐帧上屏，用户看到的效果是"画面从水印状态直接变成最新状态"，中间没有闪烁滚动。
- 这不是新机制，是把已有的 coalesce 惯例（`AgentInputRenderRegressionTests` 里"合并喂应保持稳定"）
  **扩展到重连路径**，并作为 §2.15.2 验收测试的一部分：开盖那一刻，画面只变一次。

### 2.15.3 设计题 ③：多窗口规则（多显示器的现实 vs "一扇窗"哲学）

> **✅ 已批复（2026-08-14 02:0x）：窗口规则确认，并追加"统一管理"设计（见下）。**
> **✅ 二次批复（02:1x）：几种切换行为都可实现、做成选项；默认 = 推送窗口到前台（`Enter` = 去它那里），更符合直觉。**

多显示器工作时，"把监控工作区钉在副屏"是正当需求，但窗口自增殖正是 iTerm2 之败。基础规则三条：

1. **窗口只由用户显式创建**，产品永不自动开窗。
2. 每个窗口都是完整对等的 Muxterm（自己的工作区 tab 集合），不存在"主窗口/工具窗口"之分。
3. **注意力是全局的**（菜单栏项 + Dock badge 不属于任何窗口）；面板动作里加一条"把工作区移到新窗口"。

**统一管理（项目负责人追加的设计，展开如下）：**

**(a) 面板必须显示"工作区此刻在哪个窗口"。** 标记体系：

| 标记 | 含义 |
|---|---|
| 实心高亮 | 当前窗口、当前工作区 |
| `⧉2` 类角标 | 已在**另一个窗口**打开（角标 = 窗口序号） |
| 无标记 | 已连接但没在任何窗口展示 / 未连接 |

**(b) 切到一个"已在别的窗口打开"的工作区时，两种动作，语义分开：**

| 按键 | 动作 | 实现 | 备注 |
|---|---|---|---|
| `Enter`（默认） | **去它那里**：把那个窗口推到前台并聚焦该工作区 | macOS 侧就是 `makeKeyAndOrderFront` + `activate` —— **原生、廉价、零风险**，这正是 macOS 应用的惯例（文档已打开就带你去那个窗口） | 项目负责人问"GUI 推窗口好不好做"——**很好做**，这就是默认路径 |
| `Cmd-Enter`（显式） | **拿到这里（互换）**：目标工作区来当前窗口，当前工作区去对方窗口 | 两侧各做一次 pane 重挂载；tmux 侧无感知（session 不动，动的只是"哪个窗口在渲染它"） | 满足"我人不动、工作区过来"的场景；**必须是显式动作**，默认永不隐式搬动（位置即记忆） |

**(c) 同一工作区双窗口同时渲染：v1 不做，规则先记下。**
tmux 一个 session 只有一个网格尺寸，双渲染必有一方失真。项目负责人给的规则是对的，原样记录：
**时间上第一个 attach 的窗口拥有尺寸控制权，第二个窗口做只读镜像、自适应缩放/留边（letterbox）。**
等 v1 的 (a)(b) 用顺之后再评估是否真的需要。

**(d) 丝滑是硬指标。** 切换（无论去它那里还是拿过来）观感必须与单窗口内切 tab 同级：
无闪烁、无重排动画堆积、焦点一步到位。做不到丝滑的方案宁可不上。

### 2.15.4 新点子：「上次看到这里」—— 位置即记忆的时间版

多工作区生活方式的高频时刻：**切回一个两小时没看的工作区，面对一墙 scrollback，"我上次看到哪了？"**
聊天软件早就解决了（未读分割线），终端世界没有人做。而 Muxterm 恰好万事俱备：

- 每 pane 记录"上次可见时的副本行号 + 时间戳"（副本已是唯一事实源）
- 切入时在那个位置画一条**客户端侧覆盖层**分割线（"── 上次看到这里 · 2h 前 ──"），
  一个快捷键跳到分割线；绝不修改 pane 内容（客户端身份纪律）
- 与 OSC 133 组合出**一行 catch-up 摘要**（显示在 peek 面板或分割线上）：
  *"自上次：跑了 5 条命令，1 条失败（exit 2），最后一行：…"* —— 133 的 D 参数直接给退出码

成本：副本 + 焦点跟踪，几乎白拿；依赖项就是 #1 的 scrollback 地基。
**这是"面板从导航变观察"（§B.4）的自然延伸：切换的目的既然多半是看一眼，就把"看哪里"也答了。**
定位：阶段 C 前后的甜点，不进阶段 B 的完成定义。

> **✅ 已批复（2026-08-14 02:0x）：确认，并由项目负责人追加两个同族点子（"这个很早就想要了"）：**

**追加 ①：「跳到最新」悬浮按钮（聊天软件的回底按钮）**

- 用鼠标滚上去之后，右下角出现一个小胶囊按钮；有新输出时显示计数（"↓ 最新 · +37 行"）。
  点击或快捷键 → 回到实时尾部。
- 配套语义（缺了它按钮就没意义）：**向上滚动即挂起自动跟随（scroll lock），新输出绝不把人拽回底部**；
  回底后恢复跟随。SwiftTerm 侧若已有此行为则只补按钮与计数。
- 归属：**终端基础手感**（§2.9 清单"选择/复制手感"同级），不排队等阶段，随手做。

**追加 ②：命令时间轴细轨（AI 对话式的"一条条钉住，点击跳转"）**

shell 的天然结构和 AI 对话一样是**回合制**（prompt → 命令 → 输出），OSC 133 恰好把回合边界给了：

- 在滚动条一侧叠一条**极窄的标记轨**（十像素级，悬停才展开），每条命令一个刻度：
  正常命令 = 中性刻度，**失败命令（exit ≠ 0）= 红色刻度**（133 的 `D` 参数直接给退出码），
  用户手动钉住的位置 = 星标刻度。
- 点击刻度 → 跳到那条命令；悬停 → 浮出命令文本；`[` / `]` 键盘上下条命令（Ghostty 的 prompt-jump 同款，但可见、可点）。
- **纪律：这是终端上的覆盖层注解，不是侧边栏** —— 无内容面板、默认近乎不可见、在底部实时跟随时自动隐藏。
  宽度超过一个字符位就算违规。
- 依赖：OSC 133（阶段 B 的输入）+ scrollback 副本。归属：阶段 C 同期（与搜索共享"跳转到副本坐标"机制）。

这两条与「上次看到这里」合成一族：**scrollback 不再是一堵匀质的墙，而是有地标的时间线** ——
未读线（上次看到哪）、回底按钮（现在在哪）、命令刻度（中间发生过什么）。三者共享同一套副本坐标机制。

> "TOML 唯一事实源"两项已确认；分发与首跑体验两项待发布期定稿。**

### 2.15.6 工程护栏（防止把今天的优点做没了）

1. **录制回放是标准 bug 工作流**：控制模式字节流（`%output` 序列）可录制、可回放成回归测试 ——
   `AgentInputRenderRegressionTests` 已经在这么做，**把它升格为惯例**：每个真实世界 bug 先录流，后修复。
   阶段 B 的状态机同样用录好的流喂（含时间戳），不依赖真机 tmux。
2. **scrollback 内存预算要先算账**：10k 行 × ~200B ≈ 2MB/pane；200 个 pane ≈ 400MB —— **会吃掉"占用低"这个已验证卖点**。
   规则：活跃 pane 全额（10k），后台 pane 缩额（~2k），全局预算（如 256MB）+ LRU 裁剪。数字可调，**预算机制必须有**。
3. **状态检测的性能预算**：只在整行完成时评估正则、每 pane ≥100ms 防抖、只看最后一行非空文本。
   40 工作区 × 高频输出下，检测管线不允许出现在 profiler 前排。
4. **输入延迟的诚实边界**：按键回显受 RTT 约束，这是 SSH + tmux 的物理事实。
   **v1 不做 mosh 式预测回显**（复杂度巨大，且属于运行时/传输层的活）；
   本地能救的都救（滚动/选择/搜索走副本 = 零延迟）。若 Superlogical 协议落地为 Runtime，预测问题由协议解决。

### 2.15.9 从 iTerm2 tmux 集成的 13 年里值得偷的东西（2026-08-14 02:1x 核查）

> 来源：[iTerm2 tmux Integration 官方文档](https://iterm2.com/documentation-tmux-integration.html)、
> [iTerm2 Preferences 官方文档](https://iterm2.com/documentation-preferences-general.html)（tmux 节）。
> 筛选原则：只收与身份相符的；AI 全家桶、浏览器、密码管理器等按 §2.2/§2.12 直接过滤。

#### A. 必须抄的三件 —— 每一件都在治 Muxterm 已知的伤口

**A1. 流控 / 暂停机制（tmux ≥ 3.2 的 `%pause`）—— 治"20GB 挂起"那类 bug。**

iTerm2 设置项原文：*"Pause a pane if it would take more than X seconds to catch up"* + 预警 + 自动恢复。
背景：pane 疯狂输出时，控制模式客户端会积压出巨大缓冲 —— **这正是 `tmux/backend.rs` 回归测试里
"大量 %output 曾把 events 撑到 ~20GB"的同一类故障**。tmux 3.2+ 原生支持对控制客户端按 pane 暂停
（`pause-after` 标志 + `%pause` / `%continue` 通知）。

Muxterm 版设计：落后超阈值 → 让 tmux 暂停该 pane → UI 上该 pane 角落一个小标记（不弹窗）→
追平用 capture 快照 + 自动 continue。**输出风暴从"客户端雪崩"降级为"一个 pane 短暂降帧"。**
归属：阶段 B 前后的健壮性项，与 §2.15.2 韧性同族。

**A2. 大 session 不炸开（Dashboard 阈值的 Muxterm 版）。**

iTerm2：attach 到超过 N 个 window 的 session 时不全部展开，改开 Dashboard。
Muxterm 版：attach 大工作区时**懒物化** —— 只实体化活跃 window，其余进面板按需展开。
这与"20 个工作区随时可切"的承诺互为保障：**可切 ≠ 全渲染**（§2.14.1 ③.5 同一原则的窗口内版本）。

**A3. 后台压缩 scrollback —— 补进 §2.15.6 的内存预算。**

iTerm2 设置项原文：*"Compress scrollback history in the background... significantly reduce memory usage."*
Muxterm 版：不活跃 pane 的副本在空闲时压缩（行文本压缩率极高），预算护栏从"LRU 裁剪"升级为
"先压缩、后裁剪"两级 —— **万级 scrollback 与"占用低"卖点可以兼得**。

#### B. 值得抄的手感细节（喂给 §2.9 的"终端基础"清单）

| 细节 | iTerm2 的做法 | Muxterm 落点 |
|---|---|---|
| **远程复制落本地剪贴板** | tmux paste buffer 镜像到系统剪贴板（设置项）+ OSC 52 | 远程 vim/CLI 里复制 → macOS 剪贴板直接有。**安全模型照抄**：写剪贴板 = 开关授权；**读剪贴板 = 每次弹确认** |
| **双击选中整个路径** | "Characters considered part of a word"（把 `/-_.~` 计入词字符） | agent 输出满屏路径，双击整选是日常刚需；作为默认而非选项 |
| **拖入文件自动加引号** | "When pasting a dropped filename, wrap it in double quotes" | 拖拽投递（阶段 E 前身）顺手带上 |
| **多 client 灰边** | "窗口永不大于最小客户端，多余区域显示灰边" | 恰是 §2.15.3 (c) 镜像 letterbox 规则的 13 年先例，实现时照此语义 |

#### B+. 改判（02:2x 批复）：tmux status bar 镜像 —— 从"不抄"改为"抄"

> 项目负责人："tmux status bar 也是我想要的，是不错的东西。"

原判"状态表面只有红点与面板"针对的是**通知**；status bar 是**信息**（session 名、host、
git 分支、时钟、用户自定义脚本）。用户多年调教的 status-left/right 是既有资产，
GUI 化之后凭空消失是倒退，不是简洁。

**机制（2026-08-14 02:25 CST 核查，来源：tmux man page `refresh-client -B` 节 +
[tmux 官方 wiki Control Mode 页](https://github.com/tmux/tmux/wiki/Control-Mode)）：**
tmux ≥ 3.2 给控制模式客户端提供**格式订阅** ——
`refresh-client -B <名>:<范围>:<格式>` 订阅任意 format 的展开值，变化时推送
`%subscription-changed` 通知（至多 1 次/秒）。iTerm2 的镜像选项即依赖此通道。

Muxterm 版：每工作区订阅 `#{T:status-left}` / `#{T:status-right}` 的展开值，
渲染为工作区视图底部一条**细原生条**（可关）。零轮询、零 ANSI 解析、每秒至多一次更新。

**顺手的大红利 —— 同一机制是阶段 B 的推送通道：**
`refresh-client -B state:%*:#{pane_current_command}` = session 内每个 pane 的前台命令
一变化 tmux 就主动推送。pane 检测从"轮询/猜"变成"被告知"，与 OSC 133、BEL 三路互补，
1 秒节流对注意力场景绰绰有余。**阶段 B 的 tmux 侧感知应以订阅为主干**。

#### C. 明确不抄的（记录下来防止将来心痒）

| iTerm2 功能 | 不抄的理由 |
|---|---|
| Instant Replay（时间回放） | 未读线 + 命令刻度（§2.15.4）已覆盖"刚才发生了什么"，成本低一个量级 |
| 粘贴/命令历史落盘 | 违反"不落盘、不建索引"纪律（§4.1） |
| Python API / 脚本体系 | 生态出口走只读接口（阶段 E，形态见 §2.15.10 发现二），面小得多 |
| AI Chat / 浏览器 profile / 密码管理器 | §2.2 / §2.12，Warp 判据直接毙 |

#### D. 一条元观察

iTerm2 的 tmux 设置只有**八九个选项**，却支撑了 13 年的日用 —— 每一个都对应一类真实故障
（积压→pause、窗口爆炸→dashboard 阈值、gateway 碍事→bury、剪贴板断裂→镜像）。
**它没有一个选项是"功能"，全是"止痛"。** 这与本文档"深度优先于广度"的定案完全一致：
阶段 B 之后 Muxterm 需要的正是这类止痛清单，而不是新表面。

### 2.15.10 2026 新终端扫描：最近在火什么、有什么可偷（2026-08-14 02:25 CST，HN/GitHub 核查）

应项目负责人要求扫了最近的新终端与 HN 讨论。三个发现，按重要性排序。

#### 发现一：一个"tmux + agent"民间生态已成型 —— 全在土法重造阶段 B

- **jmux**（[Show HN 2026-04](https://news.ycombinator.com/item?id=47650233)）：作者自述
  "并行跑 5–10 个 Claude Code，试过 Conductor/cmux/GUI 编排器都不对味 —— 它们要么让我
  离开 tmux 进一个 100MB+ 的 Electron，要么是没解决问题的薄包装"。做法：**agent 完成时
  session 上出橙色旗标**、无前缀键即时切换、按项目 + git 分支自动分组。~1800 行 TypeScript。
- **tmux-pilot / poly 讨论串**（GitHub）：另一批人"每天 6+ 个并行 agent"，用 `capture-pane`
  轮询 + 正则猜状态，自评 *"super brittle —— 不同 agent 的空闲态格式都不一样，最后维护一堆正则"*；
  他们点名最想要的能力是 **"send a new prompt to a specific session without switching to it"**。
- **TermHub**（Show HN）：给 agent 用的"终端控制网关"—— agent 作为终端的*客户端*。

**判读：**全部是单机、TUI 层、几百到几千行的薄包装。需求真实到被反复土法重造，而痛点
（正则猜状态脆、切换成本高、跨 session 无聚合）恰是阶段 B 的正面答案。三个具体印证：
① "末行正则开放给用户"方向对，但 **OSC 133 优先**更对 —— 这批人正陷在正则地狱里；
② **面板一行答复**再次被野生需求原话点名（继 HN agent-manager 串后第二个独立来源）—— 此案铁了；
③ jmux 的"按项目 + git 分支自动分组" = §2.15.8 工作区分组备忘的野生实现，路线确认。

#### 发现二：AI-first 终端集群（2026 春夏批）—— 三个原语反复出现

| 项目 | 规模 | 拿走的观察 |
|---|---|---|
| **Terax**（Tauri ADE，8.9k★） | 最大 | Warp/ADE 路线（编辑器 + git graph + 侧栏 AI），不在我们车道；其 "Spaces 跨启动恢复布局"与 §2.14.1 ③.5 重启恢复一致 |
| **Termany** | 小 | **从输出给 pane 打 working/done/error 标签**（原语第 N 次出现）；Zen mode（单 pane 悬浮于调暗背景）是好的专注交互 |
| **Teru**（Zig，1.6MB，自带复用器） | 小 | 发明 **OSC 9999 "agent 自我声明"**（agent 主动告知终端"我是 agent、在哪个 pane"）+ 进程图谱 + MCP server |
| **Tonn**（wgpu + MCP） | 极小 | 内置 MCP server 把终端内容按 block 暴露给 agent（`get_recent_blocks` / `search_blocks`） |

**判读：**新终端不约而同长出三个原语：(a) **pane 状态标签** —— 印证阶段 B；
(b) 终端内容经 **MCP 结构化暴露给 agent** —— 提示阶段 E 生态出口的候选形态升级：
**只读 MCP server**（暴露跨机工作区状态 + scrollback 搜索）可能比裸 socket `status --json`
更顺应真实消费者，因为 2026 年"读终端状态的程序"大概率是个 agent。跨机聚合的 MCP 无人做过。
仍维持只读纪律，不因此提前动工；
(c) **agent 经 OSC 自我声明** —— 进观察单：若形成事实标准，Muxterm 是最便宜的受益者
（读一行转义序列白得 agent 身份），无需下注。

#### 发现三：Zellij 已长成"现代 tmux"，两个交互值得抄

Zellij 0.43/0.44（2026-03 前后，[官方发布记](https://zellij.dev/news/remote-sessions-windows-cli/)）：
内置 web client（含**只读分享 token**、`zellij watch`）、原生 Windows、批量 pane 操作、
未聚焦 tab 的 **BEL 转发 + 视觉标记**（注意力原语收敛的又一证据）。

值得抄的两个交互：

1. **钉住悬浮 pane**（pin floating pane，always-on-top；官方文案 *"perfect for monitoring
   commands while working"*）。Muxterm 版：把任意 pane 钉成小悬浮窗，**跨工作区切换仍在最上层**
   —— "盯着一个 log 干别的活"是注意力论题的自然延伸，且可直接复用 peek 窗口（§B.4）的实现。
   归属：阶段 B 之后的候选，不进 1.0 门槛。
2. **原子 show/hide**（区别于 toggle）：面板/悬浮类 UI 的快捷键应有确定性语义（按下必显示，
   而非按当前状态翻转）—— 盲操作友好、实现零成本，QuickConnect 面板照此设计。

Zellij 本身**进观察单**：它没有 tmux -CC 式控制协议（插件/API 是另一套），暂不能当 Runtime；
若未来暴露结构化客户端协议，即为 tmux、Herdr 之后的第三个 Runtime 候选。

#### 结论

这一圈没有动摇任何已定决策，是三重加固：阶段 B 的原语被全行业反复发明（但全在单机/TUI 层
土法实现）；**跨机聚合依然无人碰**（五轮修正：Herdr YC 商业方向已指向"连接机器"，
判断收窄为"无人以零账号客户端形态做"，§2.17.2）；生态出口的消费者画像更清晰（是 agent）。
增量收获：两个便宜交互候选（钉住悬浮 pane、原子 show/hide）、一个形态升级选项（MCP 只读出口）、
两条新观察单（OSC agent 自声明、Zellij 客户端协议）。

### 2.15.11 TUI 阵营的 GUI 出路盘点：为什么 Herdr 们补不上这个洞（2026-08-14 02:25–02:30 CST 核查）

> 起因：项目负责人判断"HN 的 tmux+agent 需求基本被 Herdr 收割了，但它解决不了 GUI 问题 ——
> 他们有什么办法吗？"答案：有四条出路，**每一条都是胶带**，且胶带的形状恰好画出了 Muxterm 的座位。
> 来源：[herdr.dev 官方配置文档](https://herdr.dev/docs/configuration/)、
> [herdr-notifications 插件（crates.io）](https://crates.io/crates/herdr-notifications)、
> [herdr-focus-notify 插件（GitHub）](https://github.com/yankewei/herdr-focus-notify)、
> Claude Code 通知配置指南与 ntfy/Tailscale 实践帖。

#### 四条出路，逐条验尸

**出路 ① TUI 内 toast（Herdr `ui.toast.delivery = "herdr"`，默认）。**
在布局角落画一个文本框。只有你正盯着那个终端窗口才看得见 —— **不看屏幕就等于没有通知**，
这不是通知，是装饰。Herdr 也知道，所以还有 ②③。

**出路 ② 转义序列接力（`delivery = "terminal"` / Claude Code OSC 9/777）。**
链条：agent 发 OSC → tmux **默认吞掉**（需 `allow-passthrough on`，tmux 3.3+；裸 OSC 要
`all`，3.4+）→ 外层终端必须恰好支持（Claude 的 `preferredNotifChannel` 枚举值就三个：
`iterm2` / `kitty` / `ghostty`，其他终端 auto 档"什么都不做"）→ macOS 还要给那个终端 App
授过通知权限。四个失败点串联，**且客户端一断开整条链死亡** —— 而"断开后继续跑"恰恰是
Herdr 的招牌场景（官网原文："nobody is attached to any of it right now — that's the point"）。

**出路 ③ shell 出去借本地通知器（`delivery = "system"` + 社区插件）。**
Herdr 官方文档自己承认的细节，比任何批评都锋利：
- `system` 档先找 `terminal-notifier`（要用户 `brew install`），找不到降级 `osascript` ——
  降级后通知在通知中心里**显示为"Script Editor"**，且"**cannot activate the hosting terminal**"
  （点了不能回到终端，文档原话）。
- 社区补丁 `herdr-focus-notify`：要再装一个 `alerter` 二进制，还要用户**手写环境变量**
  `HERDR_FOCUS_NOTIFY_ACTIVATE_APP=kitty` 告诉它"我住在哪个终端 App 里"——因为 TUI
  自己不知道。点击后两跳：先 AppleScript 激活终端 App，再 `herdr agent focus <pane>`。
  故障排查表里赫然一行："Click does not bring forward the expected terminal"。
- 就算全装对了：**远程场景整条路无意义** —— herdr 跑在远端机器上时，`system` 档的通知
  发到*远端机器的*通知中心，那里没有人。

**出路 ④ 干脆跳过桌面，推手机（ntfy.sh / Pushover / Telegram bot + Claude hooks）。**
民间最流行的方案（有人用 Tailscale 自建 ntfy 保隐私）。这其实是**对桌面问题的投降书**：
人坐在 Mac 前面，通知绕地球一圈落在手表上。单向、无状态、不能跳转到 pane、不能回复，
但它意外证明了一件事 —— **用户要的本来就是跨机器聚合**，他们已经在用手机当穷人版聚合面板了。

（潜在出路 ⑤：学 Zellij 做 web client/PWA。浏览器里重新实现一遍终端渲染，换来二等公民的
通知能力，且只能展示自家 runtime。是条真路，但通向的是浏览器标签页，不是桌面工位。观察单。）

#### 根因：四样东西，只有"拥有连接的原生常驻客户端"才拥有

| 缺的东西 | TUI 阵营的现状 | Muxterm 对应决策 |
|---|---|---|
| **OS 身份** | 借 osascript 显示成"Script Editor"；权限、图标、声音全是别人的 | 签名 App bundle，通知/Dock badge/菜单栏红点是自己的（§2.14.1 ③） |
| **点击回跳** | 两跳接力 + 手写环境变量猜宿主终端，"best effort" | 通知→窗口→工作区→pane 是**同一个进程内的一次跳转**（§B.1） |
| **不依赖 attach** | 转义链断开即死；hook 在远端机上放空炮 | **窗口可关，感知常驻**：菜单栏项持有 control-mode 轻连接（§2.14.1 ③.5）|
| **聚合面** | N 条 session × M 台机器的通知砸成一堆无序横幅，或散落在手机上 | 红点 + 面板：按紧急度排序的单一分诊面（§B.2） |

#### 判读

1. **"Herdr 收割"对 Muxterm 是利好，不是威胁**：民间需求整合成一个有结构化事件流的
   runtime（`pane.agent_status_changed`: idle/working/blocked/done —— 这正是 Herdr-as-Runtime
   要消费的接口），detection 层有人替我们做熟了，**delivery 层的座位反而更空了**。
2. Herdr 补 GUI 洞的唯一彻底办法是自己发原生客户端 —— 那它就变成了 Muxterm 或 Superlogical。
   在那之前，它的插件生态会持续生产胶带，每一卷胶带都是这个洞存在的广告。
3. herdr-notifications 插件的去重语义（状态不变永不重发；blocked→working→blocked 算新事件，
   重新通知）与 §2.15.1 红点清除规则不谋而合 —— 独立收敛，采信。
4. 能填这个洞的实体只剩两类：**Muxterm（聚合多 runtime 的原生客户端）与 Superlogical
   （垂直整合的原生客户端）**。§2.14 钳形定位不变，紧迫感 +1。

## 2.17 四个判断题：堆功能、VC 在买什么、AI 控终端、为什么没人做过（五轮续，2026-08-14 02:5x CST）

> 起因：项目负责人对 §2.15.10/§2.16 竞品面的四连问。事实全部联网核实
> （[Conductor YC 页](https://ycombinator.com/companies/conductor)、
> [Herdr 加入 YC 官方博客](https://herdr.dev/blog/herdr-is-joining-y-combinator/)、
> [Herdr YC 页](https://www.ycombinator.com/companies/herdr)）。

### 2.17.1 为什么新终端都在堆文件系统 / git / web —— 正确的边界是"协议，不是产品"

动机拆解：终端本体无法收费（Warp 已证明）→ 融资叙事需要 TAM → 膨胀成"ADE / 工作台"。
内核需求是真的 —— agent 时代的**验证闭环**（agent 干完活，人要看 diff、跑测试、开 PR）——
但答案是错的：把编辑器/git graph/浏览器塞进终端 = 正面撞 VSCode/Cursor 的分发与生态。
项目负责人判断采信：这些产品真正想当的是 "Codex 桌面端 / Cursor Agents / Conductor"，
在那个位置它们打不过原厂。

**边界原则（成文）：协议，不是产品（protocols, not products）。**
终端提供渲染能力（图片、OSC 8 超链接、133 / 9;4 / 52），产品留在 CLI 里：
git 的好体验属于 delta / lazygit / tig + 一个渲染出色的终端，不属于终端内置 git 面板；
文件系统同理（eza / yazi 是 CLI 的事）。项目负责人"插件或 CLI 参数配合渲染"的直觉即此。

Muxterm 落点：§2.2 不做清单不动摇；**插件系统无限期不做** —— 终端的插件系统就是
转义协议本身（人人能用、零维护税、无路线图绑架）。Herdr 插件市场首月 500+ 是
社区压力机器的实证：开了插件口子，路线图就不再完全属于你。唯一出口仍是阶段 E 只读状态导出。

### 2.17.2 VC 到底在投什么（三例核实，2026-08-14）

| 公司 | 核实事实 | 变现方向 |
|---|---|---|
| **Conductor** | YC S24；2026-03 Series A **$22M**（Spark + Matrix，累计 $22.6M）；6 人；App 免费 | 官方口号 "the human interface to AI organizations"；座席 SaaS（协作/策略/审计） |
| **Herdr** | **YC F26（2026-08 宣布）**；独立开发者 Can Celik；5 个月 25k 星 / 36 万下载 / 插件市场首月 500+；宣布前主动 AGPL → Apache-2.0 | 创始人原话：*"a laptop, a VPS, a sandbox … Herdr can run anywhere today, but those machines are disconnected. **They should be connected.**"* —— 商业层 = 连接多机的协调面 |
| **Superlogical** | §2.16.1 已述：Amplify + Notable；web/macOS/iOS + 实时协作 | 未公布；预测 open-core（§2.11.6） |

**三例同构：VC 买的不是终端，是 agent 并行工作流这一层的所有权**，变现终点全是
teams / fleets / governance / 托管连接。个人开发者 = 分发渠道，企业 = 收入。
这第三次验证 §2.11.7："自有机器、不要账号"的个体是结构性无人收割的群体 ——
三家拿钱的没有一家**能**为这个群体优化，钱不允许。

⚠️ **一条实质更新**：Herdr 的商业方向（"连接机器"）与"跨机器聚合无人做"（§2.10）开始相交。
判断修正为：**"无人以零账号、客户端侧、SSH 直连的形态做跨机聚合"** —— Herdr 连接机器
几乎必然经账号/托管中继（YC 公司的路径依赖），这仍是结构分野。且其"every client is just
a view … your phone"叙事反而为 HerdrRuntime 铺路（其生态已长出 Raycast 扩展 = macOS
状态面雏形）。**风险 3b 回调 🟡→🟠**：阶段 B 自有感知 + 发布提速的权重再 +1。

### 2.17.3 "AI 控制 GUI 终端"：基本没用，两个例外

项目负责人判断成立。agent 已有最好的接口 —— shell 本身；进程编排有 tmux CLI
（send-keys / capture-pane 已训练进模型，野外大量在用）。控制 GUI 不给 agent 任何新能力
（GUI 是给人的表面）；Tonn / Teru 式"MCP 控终端"解决的是 agent 没有的问题。
按 §2.12 模型正交判据：**"AI 驱动终端"是随模型增强而贬值的资产。**

两个例外，都不是"控制"：
1. **agent → 终端的单向信号**（OSC 133 / 9;4 / 自声明）：便宜、厂商中立、Muxterm 只读；
2. **终端 → agent 的只读状态导出**（阶段 E）：终端真正独有的数据不是屏幕内容
   （agent 自己拿得到），是**跨机跨 session 聚合 + 人的注意力位置**（人正在看哪个 pane）。
   能卖的是 presence，不是 control。

### 2.17.4 为什么以前没人做（四层历史巧合，兼答"我是不是疯了"）

1. **需求倒挂是近 18 个月的事。** agent 之前，"20 个并行 session 谁在等我"几乎不存在 ——
   人是打字瓶颈，一次只活在一个 pane 里。agent 把关系倒转成"N 个 pane 在干活、一个人被等待"，
   注意力才变成稀缺资源。倒挂之前，这个产品没有意义。
2. **感到痛的人手里有刚好够用的止痛药。** macOS 有 iTerm2 -CC —— 够好到杀死重做冲动，
   但 13 年不修窗口爆炸（单维护者，他的用户不跑 20 个 session）。Linux 的高手文化把复用
   解决在 WM 层（i3 / sway 平铺）——**有能力做的人恰好不痛**（项目负责人正是换到 Linux
   失去 iTerm2 后才痛醒的，样本印证）。
3. **-CC 客户端是苦役，服务端才是甜活。** 实现别人服务器的怪癖（iTerm2 踩了十几年长尾）
   vs 自己两头都控制 —— 所以 WezTerm 自建 mux、Zellij 自建协议、Superlogical 自建协议，
   没人愿意只当客户端。Muxterm 接受客户端位置恰是差异化（零迁移），而 agent 时代这个位置
   突然值钱：存量 tmux 舰队没人想搬家。
4. **实现成本刚刚坍塌**（项目负责人观察："agent 八个月，其实不用写代码了"）。
   一个人 + agents，现在付得起 -CC 长尾的账。

三个演员（Ghostty 1.4、Superlogical、Muxterm）几个月内独立撞向同一扇门，
是需求倒挂 + 成本坍塌的签名。**不是没人想到，是这扇门今年才出现 —— 不是晚了，是准时。**

硬币反面：成本坍塌对所有人生效 → 功能没有护城河，
**位置**（不可货币化人群）+ **品味**（自己的工作流特化）+ **速度**（10–11 月发布）才有。

## 2.18 编排层勘察：kanban 之死、Hermes 与"24 小时机器人"构想的归位（2026-08-14 03:00 CST 核查）

> 起因：项目负责人两个想法 —— ① YC 三家（Herdr/Conductor/Superlogical）和 Muxterm
> 在同一层；② 如果做"中间端"，形态应是"类 Hermes 的 24 小时机器人，只操作终端，让 agent 执行"。
> 来源：[hermes-agent（Nous Research，GitHub）](https://github.com/nousresearch/hermes-agent/)、
> [vibekanban.com](https://vibekanban.com/)、Nimbalyst 对比页、MindStudio 编排工具对比（2026）。

### 2.18.1 同一层，四个座位（① 的精确版）

对：**同一层 —— agent 并行工作流层**。但座位不同：

| 座位 | 占位者 | 钱把它拉向哪里 |
|---|---|---|
| Runtime（agent 的地板） | Herdr（YC F26） | 连接多机 = 托管协调面 |
| 编排工作台（review/merge 面板） | Conductor（$22.6M） | 座席 SaaS：协作/策略/审计 |
| 协议 + 全家桶客户端 | Superlogical（Amplify+Notable） | open-core + 协作层（预测） |
| **人的窗口 / 注意力路由** | **Muxterm** | **结构性无钱可赚 → 无人来抢** |

相似的是层，不同的是座位和用户。前三个座位全被资本占了，且钱强制它们服务 teams；
第四个座位只能由不需要钱的人坐。

### 2.18.2 kanban 编排的验尸报告

- **Vibe Kanban**（品类旗舰，BloopAI 出品）：**母公司 Bloop 于 2026-04-10 关停，
  官方原因"找不到可行的商业模式"**。项目转 Apache-2.0 社区维护，功能演进停滞。
- **Claude Code Dispatch**：编排作为**agent 原生能力**（Task 工具自派子 agent）——
  分解、调度、并行执行不需要外部看板了。
- 幸存者去向：Nimbalyst（kanban 并进"工作台全家桶"+ iOS）、Paperclip（任务流水线）、
  LangGraph/CrewAI（企业自建框架市场，另一个世界）。

**验尸结论（与 §2.12/§2.17.3 三角互证）：**
"给 agent 发任务"这一层正在被两头吃掉 —— 往下被 agent 原生吸收（Dispatch、Hermes 子代理），
往上被企业框架接管。**独立的个人向编排看板作为产品已经死了（Bloop 是尸检样本）。**
项目负责人两次"想过但没做"的直觉，两次都对。

### 2.18.3 Hermes 档案（核实）：那个"24 小时机器人"已经存在，而且免费

**hermes-agent**（Nous Research，2026-02 发布，Apache/开源，自托管）：
- **驻留**：VPS/自有服务器上跑成 systemd 服务，24/7；
- **触达**：单一 gateway 接 Telegram / Discord / Slack / WhatsApp / Signal / CLI，
  "Telegram 上开的对话，回终端里接着聊"；
- **调度**：内置 cron（自然语言排程）、子 agent 并行、A2A v1.0、签名 webhook；
- **手**：七种终端后端（local / Docker / **SSH** / Modal / Daytona / Vercel Sandbox…），
  且官方特性就有 **"Delegate coding to Claude Code CLI (features, PRs)"**；
- **学习**：自动生成技能文件、持久记忆、跨 session 检索。

即：**"类 Hermes 的 24 小时机器人" 不需要做 —— Hermes 本人已经免费开源地存在**，
而且项目负责人已经在用它。

### 2.18.4 归位：中间端构想 = 租 Hermes 的脑，用 tmux 的手，缺的只有 Muxterm 的眼睛

把"我要做一个中间端"分解成三个器官：

| 器官 | 谁提供 | 状态 |
|---|---|---|
| **脑**（24h 驻留、排程、消息触达、委派） | Hermes（或同类） | ✅ 已存在，开源免费 |
| **手**（操作终端让 agent 执行） | tmux CLI 本身（send-keys / capture-pane，已训练进模型） | ✅ 已存在 |
| **眼**（跨机跨 session：谁卡了、谁完了、人看过没有） | **无人提供 —— 恰是 Muxterm 阶段 E 的只读出口** | ❌ 唯一缺口 |

**结论：不建第二个产品。** 项目负责人的编排欲望的正确出口是**把阶段 E 做完**：
只读 status socket（或只读 MCP，§2.15.10 发现二），让 Hermes 读得到
"web-dashboard blocked / data-pipeline done"。届时：

> 人在外面 → Telegram 问 Hermes"谁卡着？"→ Hermes 读 Muxterm 出口回答，
> 顺手用 send-keys 处理掉能处理的 → 人回到桌前 → 打开 Muxterm 窗口收尾。

三条不变量全部无伤：Muxterm 永不自动发键（bot 是用户自己跑的另一个进程）、
零账号零控制面（socket 是本机的）、模型正交（bot 越强，眼睛越值钱）。

**附带一条概念退役：** 原风险表 #4 的 "移动交给 botmux" 更新为
"移动交给 Hermes 类驻留 bot + 阶段 E 只读出口" —— botmux 不再需要自研，
市场已把它做出来了。**阶段 E 从此有了具名的第一个消费者：Hermes。**

## 2.19 输赢解剖：为什么 Herdr 25k、cmux 26k，而 jmux 只有 72 星（2026-08-14 03:05 CST 核查）

> 起因：项目负责人问"为什么最后 Herdr 胜出，jmux 完全没人理？"
> 核查中发现一个**必须修正的情报错误**：cmux 不是无人问津的小工具。
> 来源：[manaflow-ai/cmux（GitHub）](https://github.com/manaflow-ai/cmux)、[cmux.com](https://cmux.com/)、
> [cmux Remote tmux 官方文档](https://cmux.com/docs/remote-tmux)、[jarredkenny/jmux（GitHub）](https://github.com/jarredkenny/jmux/)。

### 2.19.1 情报修正：cmux 重定级为**最近邻竞品**（此前误归类为"GUI 编排器"）

**cmux**（manaflow-ai，2026-01-28 创建）：**26,009 星**、2,200 fork、4,176 open issues。
Swift + AppKit + **libghostty** 渲染的原生 macOS 终端，GPL，免费开源，
**Mitchell Hashimoto 本人公开推荐**（"Another day another libghostty \[app\]…"）。
形态：垂直 tab 侧边栏（显示 git 分支 / cwd / 端口 / 最新通知文本）、通知环
（OSC 9/99/777 + `cmux notify` CLI 接 agent hooks，agent 等人时 pane 亮蓝环）、
Cmd+Shift+U 跳最近未读、分屏、内嵌浏览器、socket API、iOS 伴侣（终端实时同步到 iPhone/iPad）。
中文用户评价原话："代替 iTerm2……完美解决了多终端窗口排列问题。"

**更重要的是它的 Remote tmux（beta）就是完整的 -CC 控制模式客户端**（官方文档核实）：
自己解析控制流（"protocol and %begin/%end correlation fully owned by cmux"）、
**session→workspace、window→tab、pane→原生分屏 —— 与 Muxterm 的映射一字不差**、
双向桥（本地分屏→`split-window`、拖 tab→`swap-window`）、`refresh-client -C` 尺寸、
**已在用控制模式订阅**（cwd 实时更新，要求 tmux ≥3.2）、SSH 断线指数退避自动重连、
`paste-buffer -p` 括号粘贴。另有 `cmux mosh-tmux` —— 他们也撞了 mosh 不能载 -CC 的墙，
只好把 mosh 做成独立普通终端（**独立验证了 §2.15.2 的 ET-非-mosh 结论**）。

**它仍然没有的（= Muxterm 的差异化清单，逐条对着他们文档写）：**

| 维度 | cmux 现状（官方文档自述） | Muxterm 位置 |
|---|---|---|
| 前提 | 本地终端是本体，remote tmux 是**默认关闭的 beta 旗标**，"mirror **isn't restored on relaunch**" | 远程 + 持久**是前提**（§2.13），工作区跨重启永远回来 |
| 聚合 | 通知 = 单机单窗口内的环 + 未读跳转；无跨主机队列、无常驻 | 红点 + 面板 = **跨机聚合体**；窗口可关，感知常驻（§2.14.1） |
| 形态 | 永远在屏的垂直侧边栏 | 无侧栏：状态只有红点与面板（项目负责人的审美立场） |
| scrollback | **明确不做本地 reflow**（"cmux leaves reflow to tmux"）→ 继承双重仿真的全部旧疾 | 智能客户端副本（§2.11.8）：本地 reflow / 搜索 / 断线期可滚动 |
| 粘贴 | 多行粘贴退化为逐键发送（文档自认） | 走 `paste-buffer` 全量 + 确认（§2.9 发现 3） |
| 范围 | 内嵌浏览器、iOS 同步、16 语言 README —— 广度税已现（4,176 open issues） | 止痛清单，深度优先（§2.15.9-D） |

**风险面直说：** cmux 若把 remote tmux 转正 + 做跨主机聚合，就是带着 26k 星和 libghostty
做成了 Muxterm。观察变量：remote-tmux 出 beta 的速度与方向。
**机会面直说：** 26k 星证明"原生 macOS + agent 注意力"是被验证的巨大需求；
且它的 beta 文档亲手写下了自己的三个结构短板（不恢复、不 reflow、多行粘贴退化）——
每一条都在 Muxterm 已定的路线图上。

### 2.19.2 输赢解剖：72 星与 25k 星之间隔着什么

| 因素 | 赢家（Herdr 25k / cmux 26k） | 输家（jmux 72 星，npm 周下载 414） |
|---|---|---|
| **拥有一个表面 vs 包装一个表面** | Herdr 拥有 runtime（换掉 tmux）；cmux 拥有终端 App（换掉 iTerm2） | 包在 tmux 外面、住在别人的终端里 —— 两头都不拥有，是**配件**。没人的身份认同是一个配件（"我用 cmux"成立，"我用 jmux"底下还是"我用 tmux"） |
| **降低门槛 vs 要求门槛** | cmux：下载 .app 即用零配置；Herdr：curl \| sh 单二进制 | 要求 tmux ≥3.2 + bun/npm + tmux 素养（自家文档："New to tmux? Start with…"）。**agent 潮带来的新人群不会 tmux，赢家服务他们；tmux 老手自己写脚本（twork 即样本）**。jmux 的市场 = "懂 tmux ∧ 不肯自己写 ∧ 接受包装层"的空集 |
| **分发物理学** | cmux：Mitchell 背书 + libghostty 光环 + 16 语言 README + iOS 故事；Herdr：插件市场飞轮（531 个插件 = 531 个投入者）+ YouTube + 换许可证新闻 + YC 新闻 —— **反复制造新闻时刻** | 一条 9 分的 Show HN，然后安静。AGPL 又劝退贡献者 |
| **叙事朝向** | "for AI coding agents" / "the runtime coding agents run on" —— 面向浪潮 | "A tmux environment…" —— 面向后视镜（§2.16 叙事规则第三次验证） |

**对 Muxterm 的两条推论：**
1. **Muxterm 在赢家象限**：它不包装谁 —— 它像 cmux 一样拥有用户整天住的那个 App 表面
   （客户端 ≠ 配件；jmux 输在寄居，不输在不做 runtime）。前提反转（远程优先）+ 跨机聚合
   + 无侧栏，是与 cmux 同象限内的不同座位。
2. **星数期望要校准**：cmux 的 26k 有 libghostty 光环与公司肌肉，Herdr 的 25k 有插件飞轮
   与 YC 叙事。Muxterm 按 §2.14 的定义，成功线是"作者离不开它 + 几百个真用户"——
   但输赢解剖里的可迁移动作要抄足：**反复制造新闻时刻**（§2.16 的 devlog + 两轮 HN），
   **零门槛安装**（.app + brew），**agent 朝向的叙事**（已定案）。

### 2.19.3 "cmux 和 Muxterm 很像" —— 像与不像的精确表述（03:1x，续前节材料）

项目负责人的观察成立，且要说全：**像的是器官，不像的是前提。**

**像（= 收敛演化，全是验证）：** 同一层（人的窗口）、同一表面（原生 macOS App）、
同一协议选择（tmux -CC）、同一结构映射（session→workspace / window→tab / pane→split，
一字不差）、同一注意力原语（通知 + 跳未读 ≈ 红点 + 面板）。两个互不知情的团队
对同一问题给出同构解 —— **这是对 Muxterm 全部架构判断的最强独立验证**
（连"订阅是正确主干"都被他们的 cwd 订阅提前证实了）。

**不像（= 前提，而前提最难改装）：**

| | cmux | Muxterm |
|---|---|---|
| 开机第一件事 | 开一个本地 shell | **重连你的舰队** |
| 产品重心 | 桌上这台 Mac（remote 是关着的 beta 旗标） | 那些永不休眠的机器（本地反而是特例） |
| 注意力半径 | 打开着的那扇窗内（环 + 跳未读，需手工接 hooks） | 跨机聚合，**窗口关着也在**（常驻红点，被动信号免接线） |
| 形态信仰 | 永远在屏的垂直侧栏 | 无侧栏：红点 + 召之即来的面板 |
| 深度赌注 | scrollback 明确交还 tmux（不做 reflow） | 智能客户端副本（§2.11.8）—— 他们宣布不做的恰是我们最难也最值的部分 |
| 范围 | 浏览器 + iOS + 16 语言（广度） | 止痛清单（深度） |

**一句话分工（将来 README/HN 直接用）：**
> *If your work lives on your Mac, cmux is excellent. If your work lives in tmux
> on machines you SSH into, that's what Muxterm is for.*

**应对动作（并入已有计划，无新增项）：**
① 差异化必须 10 秒可读 —— README 首屏就是"舰队之窗"，不是"tmux 的原生 GUI"（§2.16.2 已定）；
② cmux 文档自认的三短板（重启不恢复 / 不 reflow / 多行粘贴退化）做成**发布日 demo 的三个镜头**；
③ 不抢 cmux 的用户（本地派 + 侧栏审美），只收无人认领的舰队派；
④ 风险 2c 的触发器已挂观察单 —— 它一旦补"重启恢复 + 跨主机聚合"，差异化收窄为审美 + 副本深度，
届时 10–11 月已发布与否就是生死线（又一票投给 §2.16.3 的提前发布）。

## 3. 推荐定位

### 3.1 主定位句（建议采用）

> **Muxterm 把你所有正在进行的工作区装进一个窗口 —— 无论它们跑在哪台机器上、由什么 runtime 托管 ——
> 永远连着，一次按键可达，并且一眼就能看出哪个在等你。**

英文（README 首屏）：

> **Muxterm puts every workspace you have in flight into a single native window — local or remote, tmux or beyond — always connected, one keystroke away, and always showing which ones need you.**

**这句话里每一个成分都在做工，不要删：**

| 成分 | 为什么必须在 |
|---|---|
| *every workspace ... single window* | 与 iTerm2 的窗口爆炸正面对立，是当前唯一已验证的差异化 |
| *local or remote* | 位置是属性不是分类轴 —— 这是 `twork` 的组织方式 |
| *tmux or beyond* | 给 HerdrRuntime / 未来 runtime 留门，且是真正有壁垒的那部分 |
| *one keystroke away* | 键盘优先、无侧边栏的产品品味 |
| *which ones need you* | 阶段 C，唯一还缺的一环 —— 提前写进定位，用来约束路线 |

**⚠️ 三轮修正（见 §2.13）：上面这句仍把"远程"写成并列属性（*local or remote*），这偏保守。**
在 agent 时代"工作跑在一台不会睡的机器上"是结构性必然，
而**整个编排器品类（Conductor / Pane / Nimbalyst）与 IDE 侧边栏形态在形态上就无法承接它**。
因此建议把它提到主语位置：

> **你的工作跑在一台永不休眠的机器上；Muxterm 是望向它的那扇窗 ——**
> **一个窗口装下全部在飞的工作区，并告诉你哪一个在等你。**

> **Your work runs on a machine that never sleeps. Muxterm is the window into it —**
> **every workspace in one place, and it tells you which one needs you.**

**取舍要清楚：** 这句更锋利、更能与本地 App 拉开身位，但它**牺牲了纯本地用户的自我代入**。
若把纯本地场景也当一等公民，则保留原句；若接受"远程持久是这个产品的世界观"，就换新句。
**建议换** —— 理由是纯本地用户本来就有 iTerm2 / Ghostty，Muxterm 在那个场景里赢不了也不必赢。

### 3.2 备选定位句

| 备选 | 评价 |
|---|---|
| **A. "跨平台的 iTerm2 tmux 集成"** | 准确、易懂、当前最接近事实。但**不值得长期使用**：它把产品钉死在"复刻一个 2011 年的功能"，而且 ivyTerm/Dispatcher/kmux/WezTerm 都在同一句话里。适合做**当前阶段的对外说明**，不适合做身份。 |
| **B. "多工作区终端"**（推荐） | 差异化清晰、可验证、不依赖 AI 叙事、不受 agent 厂商动作影响，且**与用户真实的组织单位一致**（项目/目录，不是主机）。**这是唯一一个既真实又能长期站住的位置。** |
| **C. "Agent-aware terminal workspace"** | 危险。1) 现在完全没有实现；2) Claude/Codex 一方已经在做，且做得更深；3) 一旦把身份押在 agent 上，agent 形态一变（比如都搬进 IDE / 云端），产品身份跟着蒸发。**应该作为 B 之上的一层能力，绝不作为身份。** |

**结论：以 B 为身份，用 A 做当前阶段的对外解释，把 C 降级为 B 的一个特性。**

### 3.3 长期叙事（对开发者解释）

> 终端从来不是"一个窗口"，而是"一堆一直在跑的东西"。
> tmux 解决了"东西不会死"，SSH 解决了"东西可以在别的机器上"，
> 但没有人解决"这些东西现在到底怎么样了"。
>
> 你今天的做法是：记住它们在哪，然后一台一台切过去看。机器越多、agent 越多，这个成本越是指数上升。
>
> Muxterm 做的事很窄：**把"在哪"和"怎么样了"从你的脑子里搬到屏幕上。**
> 它不替你做决定，不替你派活，不替你写代码 —— 它只保证你永远知道该把手放在哪儿，并且放上去只要一下。

## 4. 三个方向的判断

### 4.1 方向一：浏览 / 滚动 / 跨 session 搜索

**战略价值：高，但必须重新定义。**

**它不是"搜索"，它是导航。** 一旦把它当搜索做，你就会开始建索引、做持久化存储、
考虑 ANSI 剥离、考虑存多久 —— 然后一个终端产品变成了一个日志数据库产品。这是最容易失控的一条路。

正确的产品概念：

> **工作区导航（Workspace Navigation）：让"我记得有个东西"直接变成"我人在那个现场"。**

「浏览」和「搜索」应当是**同一层**：同一个入口（比如 `Cmd-P` 的延伸），
输入什么都行 —— 主机名、session 名、进程名、目录、或者一段你记得的输出 —— 结果统一是**一个可跳转的工作区位置**。
搜索结果的价值不在于那段文字，而在于它后面挂着的**坐标**。

**搜索结果最重要的上下文，按重要性排序：**
`主机 > 项目/目录 > 进程(在跑什么) > 时间 > session/window/pane`。
注意 `session/window/pane` 排在最后 —— 那是 tmux 的概念，不是用户的概念。用户记的是"那台机器上那个项目在跑 build"。

**分层（关键）：**

| 层 | 定位 | 建议 |
|---|---|---|
| 单 pane 内查找 | 就是 find bar | **直接用 SwiftTerm/VTE 自带的**，不要自己做 |
| 跨当前连接的所有 pane | 内存 scrollback 里搜 | **做**，这是甜点 |
| 跨所有主机 / 历史 / 离线工作区 | 需要持久化 + 索引 | **明确不做**（至少 D 阶段之前） |

**与 tmux copy-mode 的关系：** 不冲突，是替代。copy-mode 只能在当前 pane 内、
且要先按前缀键 —— 它正是 Muxterm 存在的理由的一部分。

**优先级（二轮修正）：排在"pane 状态感知"之后，排在图片投递、Herdr 接入、手机端之前。**

一轮评审把它排在第一，是错的。它解决的是三层痛点里的**第三层**（"不记得东西在哪"），
而第二层（"不知道谁在等我"）更痛、更便宜、也更差异化。
两者其实是同一个导航层的两半：**状态感知回答"要不要去"，搜索回答"去哪"** ——
所以状态先做，做完之后搜索结果天然可以按状态排序，两者互相增强。

**明确不做：** 持久化历史存储、全文索引、跨天/跨周的时间线回溯、日志分析、
把 scrollback 当数据库导出。

---

### 4.2 方向二：跨 SSH 的图片 / 文件 / 剪贴板

**战略价值：中等偏低，但**边界画得对的话**成本很低、体验收益很尖锐。**

**用户真正想要的不是"剪贴板同步"，也不是"远程文件桥"，而是 Agent 输入桥。**
真实场景只有一个：*我截了个图，想让远程那个 agent 看看。*
今天这件事要经过：截图 → 存本地 → `scp` → 记住远程路径 → 在 agent 里打路径。四步，而且要开另一个终端。

**正确的心智模型（就用任务书里那句，它是对的）：**

> **把本地内容投递到当前远程工作区。**

单向、有明确目标（"当前"这个工作区）、有明确产物（一个路径）。不要做成双向同步。

**分层：**

| 层 | 决定 |
|---|---|
| **最小可靠版本** | 一个动作：`把剪贴板投递到当前工作区`。图片/文件都走同一路径 → 落到远程一个**约定目录**（如 `~/.muxterm/inbox/<ts>-<name>`）→ **把路径直接贴进当前 pane 的输入行**。用户看得见文件去了哪，也看得见接下来发生什么。 |
| **进一步增强** | 反向"取回"（远程路径 → 本地）；投递前的确认预览；inbox 的 TTL 自动清理并明确告知；拖拽投递。 |
| **明确不做** | 双向同步、云端中转、文件浏览器、远程目录树 UI、Sixel/Kitty 图形协议渲染（**让终端显示远程图片不属于这条线**，那是终端模拟器内核的事，交给 SwiftTerm/Ghostty）、任何形式的网盘。 |

**关于 SSH 的天然边界：** 用户**必须**知道文件被放在哪 —— 所以路径要显式贴出来，
不能藏在后台。谁清理：Muxterm 按 TTL 清理自己的 inbox，绝不碰 inbox 之外的任何路径。
这条纪律是这个功能不失控的全部保障。

**优先级：排在方向一之后。** 它是"锦上添花的连续性"，不是"核心循环的缺口"。

### 4.3 方向三：手机端

**战略判断：不做。这是本次评审里最强的一条建议。**

理由不是"太难"，而是**这个位置已经没了**：

1. **模型厂商一方免费覆盖。** Claude Code Remote Control（扫码即用、纯出站、免费）+ Codex in ChatGPT App（含 Free 档）。你要跟"用户已经装了的 App、免费、零配置"竞争。
2. **第三方也已经挤满**：Happy / CC Pocket / Tactic Remote / Agents At Work / AnyCoding / MuxAgent / Cmd+Ctrl，全是同一套配方。
3. **它会改变产品本质。** 手机端强制引入 daemon/gateway/relay/账号/推送/端到端加密/密钥管理。Muxterm 现在的架构赌注是 **FFI 进程内、不做 SSH 认证、不做服务端**。手机端会一次性推翻这三条。一个"极轻极快的原生终端"会变成一个"带客户端的 SaaS"。
4. **它需要的桌面端抽象一个都还没有。** 稳定的工作区身份、稳定的状态模型、稳定的事件流 ——
   而工作区状态模型（阶段 B）才刚要开始做。手机端消费的正是这个模型，所以它天然只能排在最后。

**如果将来真的要做**（B/D 阶段都跑通、且有真实用户反复要求之后），正确形态是：
**只读观察 + 通知 + 极少量输入的"移动观察端"**，绝不是"缩小的终端"。
而且应当**复用已有的 relay 生态**（Tailscale / cloudflared / 现成的开源 relay），不要自建。

**手机端最有价值动作的排序（供未来参考）：** `通知 > 查看状态 > 确认(y/n) > 看输出 > 发送少量输入 > 搜索 > 上传`。
注意"看终端画面"排在很后面 —— 用户在手机上要的是**状态和下一步**，不是 80×24 的字符网格。

**Runtime 层，在 Muxterm 之下**。修正后的图：

**这张图带来的最重要的一个判断：**

> **Muxterm 的护城河不是任何单一 Runtime，而是"同时罩住多个 Runtime"这件事本身。**

Herdr 只看得见 Herdr 的 workspace。tmux 只看得见 tmux 的 session。
Claude Remote Control 只看得见 Claude 的 session。
**Muxterm 是唯一一个可以把 tmux session、Herdr workspace、本地 shell —— 本地的和远程的 ——
放进同一个切换器、而且不要求你迁移任何东西的客户端。**

这也顺带回答了"Muxterm 会不会被 Herdr 取代"：不会，只要 Muxterm 不试图去做 Herdr 做的事。
Herdr 想让你搬进去；Muxterm 的承诺恰恰是**你不用搬**。

**回答任务书的几个具体问题：**

- **Muxterm 的核心价值是 surface，不是 orchestrator。** 这个分层是合理的，且必须严格守住。
- **Muxterm 应该知道 agent 的状态，但绝不管理 agent 的生命周期。** 更准确地说：
  它甚至不需要知道"这是个 agent" —— 它只需要知道**这个 pane 在忙 / 空闲 / 在响铃要人**（见 §6 阶段 C）。
  这个抽象是 agent-agnostic 的，所以不会过时。
- **"观察与接管" vs "编排与派发" 的边界：** 前者是**同步的、以人的注意力为中心的**；
  后者是**异步的、以任务为中心的**。Muxterm 只做前者。一旦 Muxterm 里出现"任务列表"或"派发"，就越界了。
- **远程 workspace bridge 属于 Muxterm**，因为它服务的是"我现在在这个现场"这个同步语境。
  注意 Herdr 已经实现了同一个设计（本地剪贴板图片 → 远程临时文件 → 贴路径），
  这**验证了这个产品判断是对的**；但它只对 Herdr 的 pane 有效，
  Muxterm 仍然需要为 tmux pane 自己做一份 —— 而且因为 Muxterm 是 GUI 客户端，
  它拿本地剪贴板比 Herdr 这个 TUI 更自然。
- **botmux 与 Muxterm 是互补，不是竞争。** botmux 是**异步入口**（不在电脑前时通过消息通道），
  Muxterm 是**同步入口**（在电脑前时的主工作面）。**手机端如果真的需要，答案是 botmux，不是 Muxterm。**
  ——这一条同时也解决了 §4.3 的问题：你已经有一个更合适的产品来承接移动场景了。

**防止 Muxterm 变成大杂烩的唯一有效纪律：**

> **凡是"人不在电脑前"的场景，一律不属于 Muxterm。**

这一条能一次性挡掉：手机端、推送服务、账号体系、看板、聊天、异步审批、任务队列。

### 阶段 A — 日常化 【进行中：2026-08-13 完成 Day 1】

| 项 | 内容 |
|---|---|
| **核心价值** | Muxterm 是我每天真正在用的终端 |
| **核心动作** | 把 iTerm2 从 Dock 里拿掉 |
| **完成定义** | 连续 2 周只用 Muxterm，没有因为缺功能或不稳定切回去 |
| **当前进度** | macOS 端完成并 dogfood 一整天，资源占用低、性能好；Linux 端并行开发中 |

**关于前端数量（修订）。** 一轮评审建议"冻结 GTK4 + TUI"，这条建议**修正为节奏纪律而非停工**：

> **让 macOS 领先一个阶段。** 新能力先只在 macOS 上落地，在真实日常使用里验证设计，
> **设计定稿后再移植到 Linux。** TUI 与 CLI 保持为测试与自动化载体，不追 UI 能力。

理由不变（避免在未验证的设计上付 ×N 成本），但既然 Linux 端在另一台机器上并行推进且已在运行，
"冻结"是错的成本判断 —— **真正要避免的是让四个前端同时去实现一个还没想清楚的交互。**

剩余工作是补日常终端的"不可缺"项（属于核心产品未完成，不是扩展）：
单 pane find bar（直接用 SwiftTerm 自带）、URL/路径点击、鼠标选择复制手感、resize 稳定性。
顺手把 `AppKit vs SwiftUI` 的文档矛盾改掉（`TRANSPORT-PROTOCOL-ARCHITECTURE.md` §10 与
`PROJECT-STRUCTURE.md` 仍写 SwiftUI，实际是 AppKit）。

### 阶段 B — 可见性：工作区状态 【下一步，最高优先级】

| 项 | 内容 |
|---|---|
| **核心价值** | 不用切过去，我就知道哪个工作在等我 |
| **核心动作** | 扫一眼 → 直接切到那个"在等我"的工作区 |
| **完成定义** | 一个 pane 从"跑完了 / 卡住了 / 在问我"到我知道，**延迟 < 5 秒且零误报干扰** |
| **不做则不得继续** | ✅ 是。这是核心循环唯一的缺口，也是"不只是又一个 tmux GUI"的唯一证明 |
| **明确不做** | 识别具体是哪个 agent、解析 agent 输出、上下文预算、agent 专属指令、任何 agent-specific 的 UI |

**关键设计判断：把"agent 感知"降级为"pane 行为感知"。**

不要去检测"这是 Claude 还是 Codex"。要检测的是三件与厂商无关的事：

1. **在跑 / 空闲** —— 输出速率 + `pane_current_command`，tmux 直接给。
2. **在要人** —— **监听 BEL 与 OSC 通知序列（OSC 9 / 99 / 777 / iTerm2 OSC 1337）**。
   已被 [tmex](https://github.com/krhougs/tmex) 验证：Claude Code、Codex、OpenCode **本来就会发**这些序列，开箱即用。
3. **刚变化了** —— 上次看过之后有没有新输出（"未读"）。

三个好处：**成本极低**（不需要 AI、不需要解析、不需要 per-agent 适配）、
**永不过时**（新 agent 自动支持）、**覆盖非 agent**（build 完成、测试失败、服务崩溃同样受益）。

#### B.1 交互设计：手机通知模型（已定稿 2026-08-13）

一轮评审指出的设计冲突 ——「无侧边栏」与「感知需要常驻可见」矛盾 —— 的解法已确定，
形态取自**手机 App 的通知模型**：平时只有一个红点，点开是消息列表，按发信人分组，进去处理。

不加侧边栏。**分成两个表面，各自只做一件事：**

| 表面 | 只回答 | 形态 |
|---|---|---|
| **提醒位**（常驻，面积趋近于零） | **有没有**人在等我 | 状态栏/tab 栏上一个位置：有事变红点 + Dock badge + 系统通知 |
| **列表**（按需，信息密集） | **是谁**在等我 | 点红点 或 `Cmd-P` → QuickConnect 面板，按 attention 排序 |

提醒位与 QuickConnect 的入口是**同一个位置**：平时是"连接/切换"的入口，有事时它变红。

#### B.2 四条会决定成败的规则

**规则 1 — 红点只代表"卡在我这里"，绝不代表"有新输出"。**

这是这套设计唯一的致命失败模式：如果"有未读输出"也点亮红点，那么在 20 个工作区的规模下
**红点会永久常亮，两天之内退化成墙纸**。这正是通知疲劳杀死这类 UI 的标准路径。

> **红点计数 = "我是瓶颈"的工作区数量。** 正常应该是 0–3，不是 20。
> 未读输出只在列表里做次级标记，永远不参与红点。

**规则 2 — 直接采用 Herdr 的状态词表，且三种状态的"消除条件"必须不同。**

| 状态 | 语义 | 红点？ | 什么时候消除 |
|---|---|---|---|
| `working` | 在跑 | ❌ | — |
| `blocked` | **在等我的输入/批准** | ✅ | **它自己不再 blocked 时**（你答复了）—— **不是**你看了列表 |
| `done` | 跑完了、且我还没看过 | ✅ | **你看过之后**（转为 `idle`） |
| `idle` | 空闲、且已看过 | ❌ | — |
| `unknown` | 判不准 | ❌ | 保守起见不打扰 |

⚠️ **注意 `blocked` 与手机通知语义不同。** 手机是"点开即已读"，
但 `blocked` 是**活的状态不是事件** —— 你看了一眼但没答复，它仍然卡着。
如果统一按"打开即清除"处理，你会在问题仍然存在时丢掉信号。这是最容易写错的一处。

采用 Herdr 词表的额外收益：阶段 D 接 HerdrRuntime 时，
`pane.agent_status_changed` 可以 **1:1 映射进已有 UI，零改动**。现在不花任何成本，以后省一次重写。

**规则 3 — 状态向上汇总到工作区，列表列的是工作区不是 pane。**

手机通知列表按**发信人**分组，不是按每条消息一行。对应过来：
一个工作区里有 3 个 pane 需要处理 = **列表里一行 + 计数 `3`**，不是三行。

否则列表长度随 pane 数增长而不是随项目数增长，
"工作区数量增长时 UI 复杂度不增长"这个核心命题当场破产。
汇总链路：`pane → tab → workspace`（Herdr 也是这么做的）。

**规则 4 — QuickConnect 演化为分 tab 的统一切换面板（IDE Search Everywhere 模型）。**

> **本条为 2026-08-13 修订。** 一轮写的是"不要分模式，用一个排序函数把所有结果拍平"。
> 这条规则在**只有工作区**时成立，但一旦搜索进入这个面板就不成立了 ——
> **一条 scrollback 命中、一个 blocked 的 pane、一个未连接的 ssh host，三者之间不存在共同的相关性度量，
> 无法互相排序。** 强行拍平的结果是排序函数变成一堆特例。

正确形态：**一个输入框 + 一排 tab，`Tab` / `Shift-Tab` 切换检索范围**。

| # | Tab | 内容 | `Enter` 的动作 |
|---|---|---|---|
| 1 | **工作区** | 全部已知工作区，**固定顺序**（见 §2.7「位置即记忆」，不按最近使用重排）+ 底部未连接候选（ssh host / 保存的项目 / 新建） | 切到该工作区（未连接则连接） |
| 2 | **待处理** | `blocked` / `done` 的 pane，按 attention 排序 | 跳到**那个 pane**（不是工作区） |
| 3 | **搜索** | 跨已连接工作区的 scrollback 命中 | 跳到那个 pane **并把滚动位置恢复到那一行** |

先例已核实（2026-08-13）：JetBrains [Search Everywhere](https://www.jetbrains.com/help/idea/searching-everywhere.html)
正是这个模型 —— 一个输入框，All / Classes / Files / Symbols / Actions 分 tab，`Tab` 切换范围，
默认 tab 展示最近使用项。它解决的是同一个问题：**异质结果不该被迫互相排序。**

**配套的五条细则（每条都会影响手感）：**

1. **入口决定打开时停在哪个 tab。** 这是一轮规则 4 真正想保住的东西，必须保留：
   - 点红点 / 通知快捷键 → 直接打开在 **② 待处理**
   - `Cmd-P` → 打开在 **① 工作区**

   否则"我因为红点亮了才点开，结果还要按一次 Tab 才看得到"，在红点存在的唯一理由那条路径上多了一步。
   JetBrains 同样这么做：`Ctrl+N` 直接进 Classes，`Ctrl+Shift+A` 直接进 Actions。

2. **tab 顺序固定，永不动态增删。** 待处理 tab 即使为空也要在，label 带计数（`待处理 3`），
   空时置灰。**如果它会消失，"Tab Tab" 在不同时刻含义不同，键盘肌肉记忆就废了。**

3. **切 tab 时保留已输入的查询。** 这样 `Tab` 从"重来一次"变成**"换个角度重新解释我刚打的字"** ——
   打 `auth`，Tab 一下看它作为工作区名的命中，再 Tab 一下看它在 scrollback 里的命中。
   这是个小决定，但对手感影响很大。JetBrains 也是保留的。

4. **搜索 tab 的延迟特性和另外两个完全不同，不能共用同一条输入通路。**
   工作区/待处理是在几十条内存条目上过滤 —— 每次按键即时重算即可。
   scrollback 搜索要扫过多个 pane 的若干 MB —— 必须 **debounce（100–150ms）+ 异步 + 新查询取消旧查询 + 有"搜索中"状态**，
   而且**只在该 tab 激活时才跑**。直接挂到同一条"按键即过滤"的路径上，整个面板都会卡。

5. **搜索命中的 `Enter` 必须恢复滚动位置，不能只是聚焦那个 pane。**
   这一条是 §4.1"让搜索成为回到工作现场，而不是搜到一段孤立文本"的**唯一落地点**。
   少了它，搜索就退化成一个查字符串的功能。

**tab 数量的纪律 —— 三个就够，且判据要写死：**

> **只有当一类结果无法与另一类结果有意义地互相排序时，它才配拥有一个 tab。**

按这条判据：ssh host、保存的项目、"新建工作区"**不配单独开 tab** ——
它们和工作区是同一个意图（"带我去一个能干活的地方"），放在 ① 的底部即可。
同理要抵制把 Files / History / 命令面板做成第 4、5、6 个 tab。

#### B.3 两个实施顺序上的坑

**Dock badge 比状态栏红点更重要 —— 而且它容易被漏掉。**

状态栏红点只在你**已经在看 Muxterm** 的时候有用。但这个功能的全部意义恰恰在于
**你正在干别的事**。所以两个都要，且优先级是：

> **Dock badge（应用在后台时唯一有效的信号）> 系统通知 > 状态栏红点（应用在前台时）**

**系统通知对签名有硬依赖，不要让它挡住阶段 B。**

已核实（2026-08-13）：macOS 的 `UNUserNotificationCenter` 要求**合法的 app bundle + 正确签名**，
否则 `requestAuthorization` 返回 `status=NO` / `UNErrorDomain error 1`；
bundle 结构不合法时甚至会直接崩在 `bundleProxyForCurrentProcess is nil`。
参见 [wezterm#6731](https://github.com/wezterm/wezterm/issues/6731) —— WezTerm 正是被这个问题击中，
官方签名构建正常、从源码构建的全部失效。仓库里已有 `fix/macos-dmg-signing` 分支，说明这条线你已经碰过。

因此实施顺序应为：

1. **红点 + Dock badge + 列表** —— 不依赖签名，今天就能做，且已经闭合核心循环
2. **系统通知** —— 单独一步，**必须 fail soft**：未签名时静默降级为无通知，绝不崩、绝不弹错误

**最后一条，关于检测精度：先只做两个状态，不要一上来就区分 `blocked` 和 `done`。**

BEL / OSC 只能告诉你"它要人注意"，无法可靠区分"在问我"还是"跑完了"。
硬要区分就要引入启发式（输出停了 + 进程还活着 + 末行像个提示符），而启发式正是误报的来源。

> **达到"零误报"的方法是减少状态，不是把检测做聪明。**

先上 `working` / `needs-you` 两态就足以闭合核心循环。
区分 `blocked` 与 `done` 是精化项 —— 而且阶段 D 接 Herdr 之后是白送的。

> **补充（见 §2.9 发现 2）：如果同时实现 OSC 133，这条限制可以放宽。**
> OSC 133 直接给出命令开始/结束与退出码，`working` → `done` 变成**精确事件而非启发式**；
> BEL 则继续负责 agent 的 `blocked`。两者互补，三态可以在阶段 B 内就成立。
> 上面"减少状态"的原则针对的是**纯靠 BEL 猜**的情形，不针对有明确协议信号的情形。

#### B.4 深化方向：让面板从"导航"变成"观察"

当前设计里，面板回答的是"**去哪**"。但核心循环里"观察"和"切换"是两步，
而**大部分切换的目的其实只是看一眼**。如果面板能直接回答"**那边怎么样了**"，
你就省掉了整整一轮往返，而且不打扰你当前 pane 的状态。

这是这个设计里最大的、尚未被利用的杠杆。按性价比排序：

**① 待处理行直接显示"它在问什么"（最高性价比）**

`blocked` 只告诉你"有人在等你"，但不告诉你**等你什么**。而这恰恰是你决定"现在去还是待会去"所需要的唯一信息。

> 行的内容 = `工作区名 · 进程/agent名 · 最后一行非空输出`

最后那一行通常就是问题本身（`Do you want to proceed? (y/n)`、`Enter API key:`、错误摘要）。
这是"预览"压缩成一行的版本，成本极低，但**它把待处理列表从"通知列表"变成了"待办清单"** —— 差别很大。

**② 移动选中项时预览（peek）**

选中某一行时，在面板里显示该 pane 的**最后 N 行输出**。VSCode / IntelliJ 都是移动即预览。

对终端来说这个价值比对 IDE 还大：你就能**在不离开当前工作现场的前提下巡视全部工作区**。
这条直接兑现核心循环里的"观察"，而且不需要新概念。

实现纪律：**渲染静态的最后 N 行文本，不要在弹层里塞一个活的终端。**
后者会让面板变重、抢焦点、还要处理 resize，得不偿失。

**③ 默认选中"上一个工作区"，不是当前工作区**

打开面板时光标默认落在**上一次待的工作区**上，于是 `Cmd-P` + `Enter` = 在最近两个工作区之间来回切。
这是频率最高的一个操作，应该只值两次按键。VSCode 的 `Cmd-P` 就是这个行为，而且是它最受欢迎的细节之一。

配套：再给一个不开面板的直切快捷键（如 `Cmd-\``），因为只在两个工作区之间来回时，开面板本身就是多余的。

**④ 主 tab 的顺序必须稳定 —— 状态与使用频率都不得参与排序**

**只有"待处理"tab 按 attention 排序，"工作区"tab 永远不能** ——
不按状态排，**也不按最近使用排**。

因为你会记住"我那个项目在第三行"，而位置记忆正是键盘驱动界面速度的来源。
理论依据见 §2.7「位置即记忆」：这不是 UI 细节，而是多路复用第二维度（结构与注意力）的核心机制。

状态在工作区 tab 里只以**行内小标记**呈现；"最近使用"只影响③的光标默认落点，不影响顺序。
顺序稳定之后，再叠加"数字键直达第 N 项"才有意义。

**⑤ 把 `twork` 收进产品 —— 补上 workspace 概念缺的另一半**

现在"切到工作区"在产品里，但"**创建**工作区"还在一个 shell 脚本里。这是概念不完整。

`~/.local/bin/twork` 实际定义的是一个**工作区模板**：
以目录名为身份、attach-or-create、按固定形状铺 window（Monitor / Workstation / Playground）。
这三件事都应该是产品的一等功能：

- 命令行入口：`muxterm ~/proj` / `muxterm .` → attach-or-create 该工作区并聚焦窗口
- 配置里可定义默认工作区模板（几个 window、各跑什么）
- 面板里"新建工作区"走同一条路径

做完这一条，`twork` 就可以删掉了 —— **这是产品自足性的一个明确里程碑。**

**⑥ 一个独特的声音留给 `blocked`**

当你正看着**另一个应用**时，Dock badge 也进不了视野 —— 音频是唯一还能到达你的通道。
成本极低。（Herdr 的通知 API 也正是分 `none` / `done` / `request` 三档。）

**⑦ "永远连着"应当降级为"永远一键可达"**

工作区 tab 应该列出**所有已知工作区，包括当前未连接的**，选中即按需连接。

这看起来是让步，实际是架构上的一次解脱：

> 用户真正要的承诺是「**一键可达**」，不是「**全部保持连接**」。
> 于是 warm connection pool 从**必需品**降级为**优化项** —— 它让切换更快，但不再是产品成立的前提。

这同时消掉了"同时挂 N 台远程 8 小时不掉"这个又贵又脆的门槛。

#### ⚠️ 修正：「在面板里直接答复」应当**做**，而不是推迟

本文档早先把"在面板里直接答复 blocked 的 pane"列为暂不要做。
**这条判断被市场证据推翻了，现予撤销。**

理由是 §2.10 那次核查里最强的一个信号：**这是整个品类中被反复独立发明、且被使用者点名为不可替代的交互。**
agent-manager 作者说他试了同类工具最后自己写，**唯一说不通的就是这个键**：

> *"我一直缺的是**不 attach 就回答一个 agent**。在 blocked 的那个上按空格、打字、回车，
> 内容就落进那个 pane。"* —— [HN 49111394](https://news.ycombinator.com/item?id=49107749)

逻辑上它也确实属于核心循环，而我此前把循环截断了：

> 核心循环是 **发现 → 判断 → 回应**，我此前只做到"判断"就收手了。
> 20 个工作区里有 3 个 blocked，而答案通常只有一个词（`y` / `1` / `回车`）。
> **为了敲一个字符而切过去再切回来，正是这个产品存在的理由要消灭的摩擦。**
> 面板里回答不是范围蔓延，是这个循环的自然收尾。

**但当初担心的"误发到错误 pane"是真风险，所以用设计消解，而不是用推迟消解：**

1. **必须先有 peek 才能答复。** 输入框只在 peek 面板已经展示了那个 pane 的最后几行时才可用 ——
   **你永远在看着你要回答的东西回答**。这把 ①（peek）变成了它的硬前置，顺序天然正确。
2. **目标 pane 常驻显示在输入框旁**（`工作区 · 进程`），且**发送后面板不自动关闭**，
   而是原地把该行刷新为最新输出 —— 你立刻看到自己发的东西落在哪、对方怎么反应。
3. **只发送一行 + 回车，不做多行、不做粘贴、不做转义。** 这个入口的用途是"答一个词"，不是"当终端用"。
   要写长东西就该切过去 —— 这条限制本身就是防呆。
4. **不做批量答复**（一键全部 y）。这是唯一真正危险的形态，明确划掉。

**仍然暂不要做：** 免打扰 / 专注模式 —— 等红点真的吵了再说。

**这一系列深化指向一个很强的产品形态，值得作为北极星：**

> ### Muxterm 的整个 UI = 一个终端 + 一个面板。
>
> 没有侧边栏，没有菜单驱动的功能，没有第二个窗口。
> 所有"不是在打字"的操作 —— 找、看、切、连、建 —— 全部发生在同一个面板里。
> **工作区从 3 个涨到 50 个，UI 一个像素都不用变。**

### 阶段 C — 工作区导航：浏览与搜索合一

| 项 | 内容 |
|---|---|
| **核心价值** | "我记得刚才那个报错" → 直接回到那个现场 |
| **核心动作** | 同一个入口输入任意线索（项目 / 进程 / 一段输出），结果是**一个可跳转的坐标** |
| **完成定义** | 跨当前所有已连接工作区搜索命中后，一次按键人在现场，且带上下文（项目 / 进程 / 时间） |
| **明确不做** | 持久化历史存储、全文索引、跨天回溯、日志分析、把 scrollback 当数据库导出 |

详见 §4.1。核心纪律：**只在已连接工作区的内存 scrollback 内搜索，不落盘、不建索引。**

---

### 阶段 D — Runtime 扩展：接入 HerdrRuntime

| 项 | 内容 |
|---|---|
| **核心价值** | tmux session 与 Herdr workspace 出现在同一个切换器里，且**不需要迁移任何东西** |
| **核心动作** | 与切 tmux 工作区完全一样地切到一个 Herdr workspace |
| **完成定义** | Herdr 的 `pane.agent_status_changed` 直接喂进阶段 B 已有的状态 UI，**不新增任何 UI 概念** |
| **明确不做** | 为 Herdr 单独做一套 UI；把 Herdr 的 agent 语义泄漏进 Core Protocol；放弃 tmux 侧的自有感知 |

**为什么排在 B/C 之后而不是之前**（尽管它能"白拿"agent 感知）：

1. **你的真实工作在 tmux 上。** Herdr 只覆盖你主动搬进去的部分，而且 Herdr 明说
   *"Agent detection does not inspect tmux sessions launched inside a Herdr pane"* —— **两者每个 pane 上互斥**。
   先做 B 的 OSC/BEL 方案，你现有的全部工作**立刻**受益。
2. **接口先于实现。** 等阶段 B 把"pane 状态"的 UI 抽象定下来之后再接 Herdr，
   Herdr 就只是一个**更高保真度的状态来源**接进同一个抽象，而不是反过来让 Herdr 的模型定义你的 UI。
   顺序反了，Muxterm 就变成"Herdr 的 GUI"，身份就丢了。
3. **它是加分项不是命脉。** 一旦 B 成立，Muxterm 已经独立成立；Herdr 接进来是扩大覆盖面，不是补短板。

技术上的好消息：接口比 tmux 好接（`session.snapshot` + `events.subscribe` + `terminal session control`，
NDJSON、有 protocol version、官方明写支持第三方 bridge）。**这一阶段的难点是产品纪律，不是工程。**

---

### 阶段 E — 投递桥 + 生态出口（不是移动端）

| 项 | 内容 |
|---|---|
| **核心价值** | 本地内容能立刻交给远程工作；工作区状态能被上层系统消费 |
| **核心动作** | 复制 → 一个快捷键 → 路径出现在远程 pane 输入行；botmux 能读到"哪些工作区在等人" |
| **完成定义** | 图片到远程 agent 手上 ≤ 2 个动作；一个稳定的只读状态接口（CLI/socket） |
| **明确不做** | **Muxterm 自己的手机 App、relay、账号体系、推送服务** —— 移动与异步场景由 botmux 承接 |

## 8. 主动挑战（任务书 §11）

### 三条"反对继续扩张"的理由

1. **核心循环还差最后一步，而这一步最便宜。** 快速切换已经验证成立了，但"知道该切到哪"还完全没有。
   在这一步补上之前去做搜索、图片、手机端、双 Runtime，等于绕开唯一真正要紧的事去做四件次要的事。
   而且这一步只需要 OSC/BEL —— 它的性价比高到没有任何理由让位给别的。
2. **入场券区域已经拥挤。** "tmux `-CC` → 原生 tab/split"至少有 4 个开源实现，其中 ivyTerm 与 Linux 端
   技术栈完全一致、Dispatcher 已经三平台。如果 Muxterm 的对外故事仍停留在这一层，它是在一个已经饱和
   的位置上竞争。
3. **移动 + agent 观察赛道被厂商一方免费占据。** 2026 上半年 OpenAI 和 Anthropic 都已发货
   （Codex in ChatGPT App / Claude Remote Control + 桌面并行 session 侧边栏 + SSH）。
   在这条线上投入是**结构性劣势**，而且代价是把一个原生轻量客户端改造成一个带服务端的产品。

### 三条"值得继续投资"的理由

1. **"跨机器的工作区可见性"是真实且在变大的问题，且没有人在解。**
   agent 越多、机器越多，"我不知道哪个在等我"的成本越是指数上升。
   厂商方案结构上解不了（只看得见自家 session），tmux 解不了（没有 UI），
   IDE 解不了（不管远程 shell）。**这是一个真空。**
2. **终端是这个问题的正确入口。** 不是因为终端好看，而是因为
   **agent、build、日志、服务 —— 所有长期运行的东西恰好都住在 pane 里**。
   谁掌握 pane 这一层，谁就天然拥有全景视图。这个位置不是设计出来的，是结构决定的。
3. **技术基础已经到位，且赌注下对了。** Core Protocol / Runtime / Transport 的四层切分是对的
   （SSH 是 Transport 不是 Runtime，tmux 是可换的 Runtime）；不自研终端内核、不自研 SSH 认证也是对的。
   这些决定让"再走一步就能兑现"变得可信 —— 缺的不是架构，是**收敛的纪律**。

### 顺带回答几个尖锐问题

- **"是不是只是把 tmux 的复杂性换了个 GUI 包装？"** —— 如果止步于阶段 A，**是的**。
  只有阶段 B（可见性）能让它不是。这也是为什么 B 不能被跳过、也不能被 Herdr 代劳。
- **"快速切换足以形成长期价值吗？"** —— **不足以**。`fzf` + `tmux switch-client` 已经很快了。
  让速度有意义的是"知道该切到哪"。速度是必要条件，不是价值本身。
  （但要公平地说：iTerm2 的窗口爆炸问题是真的，而快速切换 + 单窗口确实**已经**解决了它 ——
  这是一个真实的、已交付的价值，只是它单独不足以构成长期护城河。）
- **"跨 session 搜索是不是开发者的想象？"** —— **部分是**。"跨主机跨时间的全局搜索"是想象；
  "我记得刚才哪个 pane 报了这个错"是真实的。所以只做已连接工作区内的搜索。
- **"远程图片会不会是小众但昂贵的功能？"** —— 如果做成图形协议/文件管理，**会**。
  如果做成"一个快捷键把剪贴板投到远程并贴出路径"，成本很小、收益很尖锐。边界决定一切。

## 9. 最终建议（三轮定案版，2026-08-14，项目负责人已确认方向）

> ### 应该把 Muxterm 当作一个**已经成立的核心产品来收敛**，而不是当作实验性架构继续扩张。
> ### 身份定案：拥有自己机器的人的终端 GUI 客户端 —— 一扇窗、一个面板、一枚红点。

**理由（三轮汇总）：**

**产品假设已经被验证了。** 2026-08-13 的一整天真实使用证明了三件事：
渲染是对的、切换是快的、资源占用是低的。**架构不再是风险，纪律才是。**

**方向判断刚刚被以最高规格外部背书。** Superlogical（Ghostty 作者，§2.11）看着同一片地形
得出同一结论：多路复用器与持久化才是关键。同时 20+ 个编排器工具证明"谁在等我"是真痛点（§2.10）。
**而两侧都没有站在 Muxterm 的位置上**：跨机器、进程无关、不搬家、无控制面、就是终端本身。

核心循环五步里，四步已经闭合，只差"一眼看到哪个在等我"这一步。而这一步恰好是
**成本最低（OSC 133 + BEL + 用户正则，不需要 AI 也不需要解析）、差异化最高
（编排器做不了跨机与非 agent，终端做不了跨 session 聚合）**的那一步。

**接下来的顺序（§2.14.5 的展开，1–2 串行，3 可并行）：**

0. **先定一个形态级决策：窗口可关，感知常驻（菜单栏项）。**
   红点挂在哪、App 生命周期是什么，取决于它 —— 必须在阶段 B 动工前定稿（§2.14.1 ③.5）。
1. **scrollback 地基（天级）：** 接上 `[scrollback] lines` 死配置、`VecDeque` 替换 O(n) 淘汰、
   上限提到万级、确立 Rust core 为唯一事实源（§2.11.8）。这是 B 的 peek 与 C 的搜索共同的地基。
   顺手自查粘贴控制字符攻击面（§2.9 发现 3，CVE-2026-26982 同类）。
2. **阶段 B 全量（主战役）：** OSC 133 + BEL + 用户 TOML 正则 → 每 pane 状态机（working/done/blocked）
   → 红点 + Dock badge + 面板 Attention tab（含 peek 与一行答复，§B.4 修正）→（签名后）系统通知 fail-soft。
   **完成定义：状态变化到我知道 < 5 秒、零误报干扰、且产物是跨机聚合体。**
3. **配置页 + QuickConnect 三 tab 补全**（作者自评清单；交互已在 macOS 定稿的部分可在 Linux 机器并行）。
4. **公开发布（五轮提前，§2.16.3）**：B 完成 + 自用 2–4 周 → 公开 repo + Show HN，
   目标 **2026-10 底–11 月**，用 §2.13 定位句，README 写清不做清单 ——
   赶在 Superlogical beta 之前；Ghostty 1.4（2026-09）带 tmux 控制模式，
   主叙事必须是注意力聚合而非 tmux GUI（§2.16.2，同时对冲风险 #0）。
5. **阶段 C 搜索**：跑在 scrollback 副本上，只搜已连接工作区内存，不落盘不建索引 ——
   作为发布后第一个大更新，再上一轮 HN。
6. **libghostty-vt 评估 spike**：time-box 一周，产出"换 / 不换 / 何时换"（§2.11 决定①）。
7. 之后按**观察单**（§2.14.3）驱动 D（HerdrRuntime）/ E（投递桥 + 状态出口）。

**永不开工清单（定案）：** 手机端、自研多路复用器 daemon（§2.11 决定②，永久封存）、
账号/控制面/云、AI Chat 及一切"模型变强就贬值"的功能（§2.12 判据）、
持久化搜索索引、agent 专属 UI 与 agent 名单集成（§2.10）。

**关于 Herdr：值得做，但排在阶段 D，且分量已下调**（真实用户口碑显示其差异化比文档薄，§2.10）。
顺序必须是"先用 OSC/BEL/正则定下自己的状态抽象，再把 Herdr 接进这个抽象"——
反过来做，Muxterm 就变成了 Herdr 的 GUI，身份就没了。Superlogical 同理：
**只以 Runtime 身份接入，且只在它的协议开放时**（§2.11.6）。

**三条不变量，作为未来一切提案的一票否决器（§2.14.3）：**

1. 永远是客户端，永远不是运行时。
2. 只做随模型增值的功能。
3. 永远不需要账号、控制面、云。

**阶段判断：** 已经进入"**个人日常工具**"。补完可见性这一步，就直接具备公开发布的资格 ——
而且那时它有一句所有竞品都说不出的话：

> "我的工作跑在一台永不休眠的机器上。几十个在飞的工作区，都在这一个窗口里，
> 我一眼就知道哪个在等我 —— 它们该在 tmux 就在 tmux，我什么都不用搬，
> 也不需要任何人的账号和服务器。"
