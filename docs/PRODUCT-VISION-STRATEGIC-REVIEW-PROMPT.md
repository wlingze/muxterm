## 2. Muxterm 的背景上下文

请把以下内容作为产品背景，并结合仓库中的产品文档理解，不要把它们当作已经完成的实现承诺。

Muxterm 当前的核心形态是：

> 一个原生、轻量、快速的终端工作空间。它连接本地或远程的 tmux/session，把多个 session、window、pane 以自己的 tab/pane UI 呈现出来，让用户可以快速浏览、切换、操作和恢复长期运行的终端与 AI coding agent。

用户实际感受到的价值不是“又一个终端模拟器”，而是：

- 同时连接多台机器和多个 tmux session；
- 用类似 `Cmd-P` 的方式快速切换；
- 不需要反复手动 `ssh`、`tmux attach`、`Ctrl-B`；
- 在一个原生窗口里观察很多长期运行的工作；
- 资源占用很小、切换很快、工作状态不容易丢；
- 未来能感知 coding agent，并在桌面、远程和手机之间继续工作。

用户日常工作环境主要是 macOS + Linux、SSH + tmux、多个 coding agent 和多个项目。Muxterm 的第一阶段目标是：

> 在 macOS 和 Linux 上成为 iTerm2 的实际替代品，尤其服务于需要同时管理大量远程 tmux/Agent 工作区的重度用户。

长期目标不是简单复制 iTerm2，也不是重新实现 Claude/Codex 等 Agent。更可能的方向是：

> **Agent-aware terminal workspace：一个能理解“我有哪些工作正在进行、在哪里进行、当前是否需要我介入”的终端工作入口。**

## 5. 方向一：浏览、滚动和跨工作区搜索

用户希望增强：

- 上滑后快速浏览大量历史输出；
- 更舒服地阅读长日志和 Agent 输出；
- 一个 session 内跨多个 window/pane 搜索；
- 跨多个 session、多个主机和多个项目搜索；
- 搜索结果能直接回到原始工作区；
- 让用户知道“某个错误/某次输出/某个 Agent 状态发生在哪”。

请不要讨论如何实现索引、如何解析 ANSI 或如何写搜索 API。请只讨论上层产品设计：

## 7. 方向三：手机端

- 在需要时发送少量输入或确认；

## 8. Muxterm、botmux、Herdr、Multica 的上层边界

请不要做代码对比，而是做产品分层和责任边界分析。

当前可以这样理解：

```text
Muxterm
  负责：终端工作空间、连接、观察、切换、搜索、接管、恢复、远程内容桥

botmux
  负责：Feishu/Lark 与 Claude Code、Codex、Gemini、OpenCode 等 CLI 的消息桥接、会话入口和远程 Web 终端

Herdr
  负责：Agent workspace/runtime、工作区和更上层的运行环境感知

Multica 或类似系统
  负责：任务、看板、Agent 分派、Runtime 调度、审核和协作控制面
```

请评估：

1. 这个分层是否合理？
2. Muxterm 的核心价值是否是“terminal surface / workspace surface”，而不是 Agent orchestrator？
3. botmux 与 Muxterm 的关系应该是竞争、互补、上下游还是可选集成？
4. Muxterm 是否应该知道 Agent 的状态，但不负责管理 Agent 生命周期？
5. “观察和接管”与“编排和派发”之间的边界在哪里？
6. 远程 workspace bridge 应该属于 Muxterm，还是更上层的 Herdr？
7. 如果未来这几个项目组合起来，用户看到的最终产品应该是什么？
8. 如何防止 Muxterm 变成一个包含终端、看板、聊天、文件管理、移动端和 Agent SDK 的大杂烩？

请画出一个简洁的产品生态分层图，并指出每个产品应该明确“不负责什么”。
