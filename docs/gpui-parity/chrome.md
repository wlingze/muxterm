# Chrome model parity inventory

This reference records the macOS rules that a gpui frontend must preserve. It compares models, not whether either frontend currently wires every helper into a visible control. The baseline is `cc952ce3`. Inventory time was `2026-11-04T15:35:28+08:00`.

## Scope and notation

| Item | Meaning |
| --- | --- |
| Swift sources | An unqualified `Name.swift:line` refers to `src/frontend/macos/Chrome/Name.swift`. All 36 files were read, totaling 9,576 lines. Counts include comments and blank lines. Reproduce with `wc -l src/frontend/macos/Chrome/*.swift`. |
| Rust sources | `linux/...`, `view_store.rs`, `command_queue.rs`, `mirror.rs`, and `utils/...` are relative to `src/frontend/`. `C` below means `src/frontend/linux/chrome/`, whose module declarations are in `linux/chrome/mod.rs:3-16`. |
| Identical | The compared rule has the same observable result for its represented inputs. This does not assert identical platform key names, DTO ownership, integration, or exhaustive differential-test coverage. |
| Subset | Rust implements part of the Swift model. The missing part is named. |
| Divergent | Both implementations decide the same question differently. The concrete difference is named. A platform-specific difference is not automatically a defect. |
| None in C | No counterpart was found in Linux Chrome. Related Rust implementations outside C are listed separately rather than counted as net-new work. Absence claims are scoped to the inspected frontend files, not to every Core module. |
| Pure? | `Yes` means a framework-independent deterministic rule or state transition with its state, time, or callbacks supplied. `No` identifies actual I/O, an implicit environment read, or global mutable state. There are **no AppKit imports in this slice**. `NSRect` geometry and strings naming AppKit appearances do not themselves invoke AppKit. See `FlatChrome.swift:1-11,204-230`. Non-pure entries therefore name their real dependency instead of inventing an AppKit dependency. |

### DTO boundary

Chrome mostly consumes its own value types rather than importing CoreBridge. The following correspondences specify what a Rust adapter must provide.

| Fact family | Swift boundary | Rust boundary and ViewStore facts |
| --- | --- | --- |
| Topology | `Tab`, `Pane`, `LayoutNode`, and workspace-keyed `StateChange` values in `macos/CoreBridge/CoreBridge.swift:8-84`. | `ClientTab`, `ClientPane`, `ClientLayout` in `utils/corebridge.rs:792-823`. `WorkspaceView.workspace`, `backend_status`, `tabs`, `panes`, and `layouts` in `view_store.rs:35-67`. |
| Targets | `CoreWorkspaceCandidate.targetConfig`, `CoreWorkspaceInfo`, and canonical resolved target conversion in `macos/CoreBridge/CoreBridge.swift:206-235,324-394`. | Target drafts and typed candidate references in `linux/ui/quickconnect/model.rs:88-98,575-609`. Do not replace the Core workspace routing ID with a local scene or Recent key. |
| Attention and agents | `AttentionSnapshot` decodes the activity JSON. `CorePaneAgentPayload` converts structured events to `StructuredPaneAgent`, and CoreBridge returns workspace-scoped snapshots in `macos/CoreBridge/CoreBridge.swift:86-118,2027-2034`. | `ClientActivitySnapshot` and `ClientAttentionPane` feed Chrome rows. The newer revisioned activity-record cache is separate in `view_store.rs:122-173`; it is not automatically equivalent to Swift's pane-agent registry. |
| History and search | `CoreCommandMark` response, Chrome `CommandMarkTick`, and `SearchSnapshot` are separate DTO projections. See `macos/CoreBridge/CoreBridge.swift:249-264`, `CommandMarkRail.swift:10-33`, and `SearchModel.swift:26-58`. | `ClientCommandMark` and `ClientSearchHit` in `utils/corebridge.rs:825-842`. Last-seen also needs a sequence-to-history-offset lookup, not just a line count. |
| Local-only inputs | Key chords, clipboard stages, editor text, timestamps, geometry, and widget focus facts do not come from Core. | These need gpui adapters, not new Core facts. Their exact input fields appear in the tables below. |
